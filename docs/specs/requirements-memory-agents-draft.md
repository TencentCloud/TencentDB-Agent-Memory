## 1. Общая цель

Память должна **реально работать** и быть **заметной**:
- собираться по проектам,
- распределяться по проектам,
- проектная память имеет **больший приоритет** в recall, чем память чужих
  проектов (чужие проекты **НЕ выпиливаются полностью**, просто понижаются),
- работают роли, которые занимаются **ДЕДУПОМ** памяти и **сбором** памяти.

«Сейчас это вообще бесполезная хуета. Стартуется проект — а агент так же о
нём не знает» (юзер, 2026-08-07).

## 2. Проблемы, которые юзер назвал

1. Инжектируемые правила (rules/*.json) **дублируются** в памяти/recall —
   нужно пометить, что их НЕ дублировать.
2. Все роли консолидации/дедупа **не вызываются** (починка вызова ролей).
3. По проектам **не собирается контекст** — агент не знает о проекте при
   старте. L2 выключен, «должен быть включен».
4. Агентный пайплайн работает не так, как надо: каждая отдельная сессия
   должна запускаться **со своими файлами, в отдельной папке**, путь до
   которой настраивается **через описание роли (role.json)**.
5. «Вынести всю эту хуюню из самого сервиса куда-то в домашний каталог,
   папку автоматически создавать, и в ней же запускать агента».

## 3. Требования: память по проектам

- [ ] R-П1. Память собирается по проектам: у каждого активного проекта
      растут записи с `project_id` и scene-блоки.
- [ ] R-П2. Распределение памяти по проектам: контекст проекта хранится
      отдельно, не смешивается с глобальным.
- [ ] R-П3. Проектная память имеет больший приоритет, чем память остальных
      проектов (recall в проекте X в первую очередь возвращает память X).
- [ ] R-П4. Чужие проекты **не выпиливаются полностью** — остаются
      доступными с пониженным приоритетом/весом.
- [ ] R-П5. При старте сессии в проекте агент **знает о проекте**:
      recall отдаёт контекст текущего проекта.

## 4. Требования: роли (дедуп, сбор, консолидация)

- [ ] R-Р1. Существуют роли, которые занимаются **дедупом** памяти
      (схлопывание дублей).
- [ ] R-Р2. Существуют роли, которые занимаются **сбором** памяти.
- [ ] R-Р3. Все роли **реально вызываются** (проверить и починить, почему
      сейчас не вызываются: dedup-daily, night-keeper, критики).
- [ ] R-Р4. Роли работают по расписанию/порогу и **применяют** изменения
      (не пустые diff'ы).

## 5. Требования: агентный пайплайн (главный фокус сейчас)

> «начинаем с агентного пайплайна, его чиним» (юзер, 2026-08-07).

- [ ] R-А1. Каждая отдельная сессия агента запускается **со своими файлами,
      в отдельной папке**.
- [ ] R-А2. Путь до папки сессии **настраивается через описание роли**
      (role.json).
- [ ] R-А3. Вся механика сессий **выносится из самого сервиса** (гейтвея)

- [ ] R-А5. Агент запускается **в этой папке** (cwd агента = папка сессии).

## 8. ЦЕЛЕВАЯ АРХИТЕКТУРА: агентный пайплайн как отдельная подсистема (2026-08-07, «пока думаем»)

### Принцип

Один универсальный пайплайн выполнения агентского рана. Ноль специализированных
режимов (никаких day/night/keeper/dedup веток). Всё разнообразие — из контракта
роли. Роль — json (декларативно) или ts-модуль (код, как экстеншены pi).
Пайплайн — отдельная подсистема `src/agents/`, не перемешанная с памятью/гейтвеем.

### Структура

```
TencentDB-Agent-Memory/src/
├── gateway/          ← HTTP-слой (тонкий): роуты, /status, /memory/run → делегирует в agents/
├── core/             ← ПАМЯТЬ: L0/L1/L2/L3, recall, scene, persona, store (не трогаем концептуально)
├── agents/           ← НОВАЯ ПОДСИСТЕМА: весь агентный пайплайн
│   ├── types.ts          — контракт роли + шаги пайплайна
│   ├── registry.ts       — загрузка ролей: roles/*.json + roles/*.ts (как экстеншены pi)
│   ├── dispatcher.ts     — ЕДИНАЯ ТОЧКА ВХОДА: run(roleName, reason); триггеры из контракта
│   ├── runner.ts         — универсальный раннер (стадии пайплайна + хуки)
│   ├── hooks.ts          — хук-точки, встроенные в runner
│   ├── spawn.ts          — спавн pi-агента (аргументы из контракта роли)
│   ├── scratch.ts        — папка сессии: mkdir, cwd, keep_scratch, cleanup
│   ├── diff-builder.ts   — построение диффа по scope роли
│   ├── caps.ts           — механические лимиты (ops_subset, caps из роли)
│   └── checkpoint.ts     — per-role курсоры
└── roles/             ← КОНТРАКТЫ РОЛЕЙ (данные)
    ├── memory-keeper.json
    ├── night-keeper.json
    ├── dedup-daily.json
    └── <custom>.ts       — опционально, код-роль
```

### Универсальный раннер (без day/night)

```
run(roleName, reason)
  ├─ 1. resolveRole(roleName)          → контракт (json | ts)
  ├─ 2. [hook] beforeRun
  ├─ 3. buildDiff(role.scope, caps)    → «Текущий дифф» (fresh_tail/full_store/over_limit — из роли)
  ├─ 4. prepareScratch(role)           → mkdir <scratchRoot>/<runId>, пишет prompt.md, diff.json, tools/
  ├─ 5. [hook] beforeSpawn
  ├─ 6. spawnAgent(role)               → pi -p … cwd=<scratchRoot>/<runId>
  ├─ 7. readAgentResult()              → diff.json из скретча
  ├─ 8. [hook] onAgentResult
  ├─ 9. checkCaps(role)                → механические лимиты
  ├─ 10. applyDiff(role.opsSubset)     → /memory/apply
  ├─ 11. advanceCheckpoint(role)       → per-role курсор
  ├─ 12. [hook] afterRun
  └─ 13. report + cleanup (keepScratch ? сохранить : rm)
```

## 8а. EVENT-DRIVEN МОДЕЛЬ: основная цепочка памяти эмитит события, экстеншены-подписчики (2026-08-07, юзер)

> «Вот конкретно подготовку файлов можно вынести в сам формат ts экстеншена, или условия вызова вообще туда прокинуть, а основная цепочка событий просто триггерит раз в какое-то время их. Типо, мы даём просто экстеншену нашему кастомному основную апишку (вызов мемори, и тд), ведём основной счётчик после добавления каждого из слоя памяти (можно в бд как постранзакционный хук), после апдейта персоны, и тд.» (юзер, 2026-08-07)

### Суть

Инверсия от «центрального раннера ролей» к event-driven:

1. **Основная цепочка памяти** (L0 capture → L1 extract → L2 scene → L3 persona) — ядро.
   У неё есть счётчики и события после каждой стадии.
2. **Счётчики — в БД, посттранзакционный хук**: после коммита добавления записей
   (+N L1 после экстракции, +1 после апдейта persona) обновляется счётчик
   «сколько нового накопилось».
3. **Агентные экстеншены — ts-модули** (как экстеншены pi): им даётся основная
   апишка (memory: recall/search/apply/records/duplicates, счётчики, spawn).
   Они сами: подписываются на события/условия вызова, сами готовят файлы для агента
   (prompt.md, diff.json, tools/), сами решают, что происходит с агентом.
4. **Основной цикл просто триггерит их** раз в какое-то время — не знает их логику.

## 8б. ООП-СХЕМА АГЕНТОВ (2026-08-07, юзер + правки)

> «Можно перейти на ооп-схему, в данном случае с pi это будет удобно, будет основной
> класс Agent, который в конструкторе получает конфиг, Класс AgentPrepare, который
> подготавливает папку перед агентом, и основные хуки. В качестве основной инициализации
> просто хук init докинуть, который будет импортироваться в экстеншн, и вызывать
> конструктор класса, а каждый агент просто делает extends этих двух основных классов
> (или более), и расширяет до кастомной логики. Как тебе такой вариант? Или можно лучше?»

### Решение агента (моё): ОК с правками

- **TS-ограничение**: `extends` только ОДНОГО класса — `class X extends Agent, AgentPrepare`
  не компилируется. Поэтому подготовка = переопределяемый шаг в `Agent`, не второй предок.
- **Template method**: базовый `Agent` держит НЕИЗМЕНЯЕМУЮ цепочку `run()`
  (shouldRun → prepare → buildDiff → spawn → parseResult → caps → apply → advance → report),
  подкласс переопределяет только шаги-хуки (`protected` методы).
- **init-хук**: `export default (api, config) => new MyAgent(api, config)` — паттерн pi-экстеншенов.
- **Подготовка**: `prepare()` — виртуальный метод с дефолтной реализацией
  (mkdir + prompt.md + diff.json + tools/); переиспользование между ролями — через
  интерфейс `ScratchPreparer` + композиция (не наследование).

### Набросок API

```ts
// базовый жизненный цикл (template method)
export abstract class Agent<Ctx = unknown> {
  constructor(protected api: AgentAPI, protected config: RoleConfig) {}

  protected shouldRun(ctx: Ctx): Promise<boolean> { return true; }
  protected prepare(ctx: Ctx): Promise<Scratch> {
    return defaultPrepare(this.api, this.config, ctx);
  }
  protected abstract buildDiff(ctx: Ctx): Promise<DiffSection>;
  protected parseResult(scratch: Scratch): Promise<AgentDiff> { ... }
  protected checkCaps(diff: AgentDiff): boolean { return checkCaps(this.config.caps, diff); }
  protected apply(diff: AgentDiff): Promise<ApplyResult> {
    return this.api.apply(diff, this.config.opsSubset);
  }
  protected report(summary: RunSummary): void { ... }

  async run(reason: string): Promise<RunResult> {
    if (!await this.shouldRun({ reason })) return { skipped: true };
    const scratch = await this.prepare({ reason });
    const diff = await this.buildDiff({ reason });
    const child = await this.api.spawn({ cwd: scratch.dir, ...this.config.spawnArgs });
    const agentDiff = await this.parseResult(scratch);
    if (!this.checkCaps(agentDiff)) return { skipped: true };
    await this.apply(agentDiff);
    await this.api.advanceCheckpoint(this.config.name);
    this.report({ ... });
    return { ok: true };
  }
}

// кастомная роль
export default (api: AgentAPI, config: RoleConfig) =>
  new (class DedupDaily extends Agent {
    protected async shouldRun(ctx) { return api.counters.get("newL1") >= 50; }
    protected async buildDiff(ctx) { return api.diff.build({ scope: "full_store" }); }
  })(api, config);
```

## 8в. КАТАЛОГ ХУКОВ (2026-08-07, юзер: «какие ещё полезные хуки докинуть можно?»)

### 1. Жизненный цикл рана (template-method run()) — обязательные

| Хук | Когда | Зачем |
|---|---|---|
| onPrepareError | mkdir/write файлов упал | fail-open: не спавнить агента в сломанной папке |
| onSpawnError | pi-процесс не запустился | явная ошибка вместо тихого exit null |
| onTimeout | агент не уложился в timeoutMs | лог + retry/пропустить/частичный stdout |
| onParseError | diff.json кривой/отсутствует | fail-open: не ронять ран, записать причину |
| onCapsRejected | мех. лимиты превышены | отклонить весь дифф или обрезать до капа |
| onApplyError | /memory/apply ошибка | retry с backoff? сохранить дифф для ручного разбора |
| onCleanup | скретч удалён/keep_scratch | пост-аудит чистки сессии |

### 2. События памяти (event-driven из §8а) — подписка, не override

| Хук | Когда | Зачем |
|---|---|---|
| onL0Captured | +N сообщений в L0 (после транзакции) | триггер счётчика «сырого» |
| onL1Extracted | +N записей L1 | ГЛАВНЫЙ счётчик — dedup/keeper смотрят на него |
| onL2ScenesUpdated | сцены пересобраны | собрать контекст проекта (память по проектам) |
| onPersonaUpdated | persona.md переписан | счётчик «после апдейта персоны» |
| onRecall | после каждого /recall | фидбек-петля: что вернулось, что пропущено |
| onThresholdCrossed | счётчик слоя > порог роли | момент «пора запускать агента» |
| onSessionEnd | сессия завершена (аналог pi agent_end) | flush-хук: доработать хвост сессии |

### 3. Окружение / lifecycle — опционально

| Хук | Когда | Зачем |
|---|---|---|
| onInit | гейтвей стартовал, роль загружена | проверить своё состояние |
| onShutdown | гейтвей гасится | снять блокировки, убить детей, дозаписать checkpoint |
| onRoleReload | конфиг роли изменился | hot-reload без рестарта |
| onConfigChange | общий конфиг памяти сменился | пересчёт порогов |

### 4. Наблюдаемость — катастрофически не хватает сейчас

| Хук | Когда | Зачем |
|---|---|---|
| onRunStart/onRunEnd | начало/конец рана | обогащённый отчёт |
| onStatusTick | периодически | /status показывает живые счётчики ролей |
| onMetric | любая стадия | счётчики для мониторинга |
| onProbeResult | precision@k посчитан | метрика качества recall |

### Обязательный минимум (для «память заработает заметно»)

1. onL1Extracted + onPersonaUpdated + onThresholdCrossed — связка «счётчик в БД
   после каждого слоя → экстеншен решает, пора ли запускать агента».
2. onTimeout + onParseError + onApplyError — fail-open трио (сейчас ошибки глотаются,
   keeper «молча успешен» с пустыми диффами).
3. onL2ScenesUpdated — ключ к «агент знает проект при старте».

### Правило добавления хуков

Базовый класс Agent объявляет хуки как ОПЦИОНАЛЬНЫЕ методы с no-op дефолтом
(`protected onTimeout(): void {}`), а не обязательные абстракты — тогда докидывание
нового хука = правка базового класса, а не всех ролей.

2. ts-роль = json + функции-хуки (как `export default (api) => {}` в pi-экстеншенах).
