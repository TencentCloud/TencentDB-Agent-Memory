### 1.1. Откуда РЕАЛЬНО берётся P1 (разбор `e362999`)

Это главный замер документа: он определяет, какой вариант вообще покупает цель.

```
36 добавленных не-тестовых .ts   32 изменённых не-тестовых .ts
──────────────────────────────   ─────────────────────────────
17  src/gateway/l1                4  consolidation/launchers
 6  src/services/l1               4  consolidation
 3  scripts                       4  core/record
 2  utils/pipeline-factory        3  utils/pipeline-factory
 2  gateway/control-plane         3  gateway/control-plane
 2  core/record                   3  gateway (корень)
 2  src/agents                    3  core/store
 1  src/repo/l1                   2  utils/pipeline
 1  consolidation/launchers       2  gateway/apply-executor
                                  1  gateway/l1 · 1 core/seed · 1 core · 1 index.ts
```

Читается так: **новый код фичи и так лёг компактно** (24 из 36 файлов — в
`gateway/l1` + `services/l1` + `repo/l1`). Дорогими были не новые каталоги, а
**32 правки в общем коде**, и они почти все одной формы: «дописать себя в
захардкоженный список» или «переобъявить ту же форму ещё раз».

Подтверждения этой формы:

* `launchers/pi-config.ts:61` — `OWNED_FLAGS_WITH_VALUE` пополняется руками.
* Форма результата объявлена трижды: `apply-executor/types.ts:47`
  (`ApplyResult`), `consolidation/runner-types.ts:26` (`RunBatchResult`),
  `consolidation/types.ts:37` (`RunSummary`) — плюс четыре места, где тот же
  объект собирается литералом (`runner.ts:24`, `summary.ts:27`,
  `busy-summary.ts:24`, `role-lock.worker.ts:71`).

**Следствие:** перенос каталогов не трогает ни один из этих 32 файлов. Значит
«вертикальные срезы» сами по себе P1 НЕ покупают. Это исправление к ревизии 1,
где B×P1 стояло ✅.

## 3. Варианты

### Вариант H. Точки расширения без переезда каталогов ⟵ новый, от архитектора

Каталоги не двигаются вообще. Убирается ровно то, что делает фичу дорогой:

1. **Один владеющий тип результата** вместо трёх (`ApplyResult` — источник,
   остальные два — производные или псевдонимы). Новое поле = 1 файл, не 12.
2. **Типизированные контракты стадий** пайплайна (вход/выход стадии — тип, а
   не соглашение), чтобы стадия добавлялась реализацией контракта.
3. **Реестры вместо литеральных списков** там, где фича вынуждена дописывать
   себя (`OWNED_FLAGS_WITH_VALUE`, разбор ролей, поля отчёта).
4. **Тест направления импортов с «дедовщиной»**: текущие 25 циклов
   зафиксированы списком, новые запрещены.

* **Лечит:** P1 по его настоящей причине, P2 полностью, P3 (останавливает рост).
* **Не лечит:** P4, P6, P8 — их надо отдельно.
* **Цена:** дни. Ни один файл не меняет путь → риск для рантайм-путей нулевой.
* **Риск:** низкий. Это E + D + C без переезда.

### Вариант A. Классические слои (layered)

`platform → domain → data → app → adapters`, зависимости строго вниз.
Обобщение того, что начато в `src/repo/l1` и `src/services/l1`.

* **Лечит:** P3 (направление), P4 (SQL уезжает в `data/`), P7 (домен без IO).
* **Не лечит:** P1 — слои ортогональны фичам.
* **Цена:** переезд ~150 файлов, механический, но упирается в §5.1 (пути).
* **Риск:** средний.

### Вариант B. Вертикальные срезы (modular monolith / feature slices)

`src/features/<feature>/{api,app,domain,data}` — фича владеет своим стеком.

* **Лечит:** читаемость границ; P1 — **нет** (см. §1.1).
* **Границы:** на живые швы ложатся `capture`, `consolidation`, `apply`.
  `extraction` НЕ ложится — он размазан по `core/record` (17), `gateway/l1`
  (23), `services/l1`, `repo/l1`, `agents`. `recall` — не шов, а стройка с
  нуля. `control-plane` — не срез, а инфраструктура (27 внешних импортёров).
* **Цена:** недели, и это самый рискованный по §5.1 вариант.
* **Вывод:** поздний, необязательный шаг. Не первый.

### Вариант C. Порты и адаптеры (гексагон)

Домен в центре, наружу — порты, реализации по краям.

* **Лечит:** P4, P7, P8, тестируемость без моков.
* **Важно:** порты здесь **заработаны** (3 лаунчера, 2 стора), а не выдуманы.
* **Ограничение:** только там, где реализаций ≥2. Иначе слой обёрток.
* **Цена:** низкая-средняя: два порта уже есть, надо доделать репозитории и
  закрыть P8 — решить владельца каждой таблицы.

### Вариант D. Пайплайн как первоклассная сущность

`capture → extract → consolidate → apply → recall` как именованные стадии с
типизированными контрактами; роли и стадии — данные.

* **Лечит:** P1 для пайплайновой половины.
* **Цена:** низкая: `role.json` уже носит половину контракта.
* **Замечание:** это пункт 2 варианта H, а не альтернатива ему.

### Вариант E. Не переезжать: закрепить правила и вычистить точечно

Тест направления импортов, распил `http-utils`, один тип результата, вынос
инлайнового SQL в существующие `*-repo.ts`.

* **Статус:** поглощён вариантом H (H = E + пункты 2–3).

### Вариант F. Событийная шина внутри процесса

Отвергнут. Один процесс, одна sqlite, синхронный поток; механизм уведомлений
уже есть (`core/record/commit-port.ts`).

### Вариант G. Разделение на пакеты/воркспейсы

Отвергнут на этом этапе: воркспейсы зафиксируют текущие 25 циклов в виде
циклических зависимостей пакетов.

## 5. Рекомендация (ревизия 2): H → C → B опционально

**Сначала H, потому что он бьёт по измеренной причине P1 и ничем не рискует.**
Потом C — он закрывает P4/P7/P8, где живёт вторая половина боли. B — поздний и
необязательный, по одному срезу, начиная с `capture`.

Целевая форма, к которой это сходится (если B всё-таки делаем):

```
src/
  kernel/        типы записей, ошибки, конфиг, платформа, control-plane
                 НЕ знает ни одного среза
  features/
    capture/ extraction/ consolidation/ apply/ recall/
  adapters/      http/ mcp/ cli/ launchers/ stores/ embedding/
  composition/   server.ts: сборка и жизненный цикл, единственное место с `new`
```

### 5.1. Чего нельзя делать наивно (иначе тихо ломается прод)

Файлы, которые ищут соседей **по своему пути на диске**, при переезде ломаются
молча — тесты и `/health` остаются зелёными:

* `consolidation/keeper-tools.ts:24` — `import.meta.url` + литерал
  `"../consolidation/keeper-tools"`; промах даёт `null` **внутри проглоченного
  catch** → роль keeper поднимется БЕЗ python-инструментов, видно только по
  содержимому ночного прогона.
* `l1/l1-role-installer.ts` — идёт вверх по дереву за `roles/`.
* Всего `import.meta.url` используют 24 файла, из них 10 не тестовые.

Плюс: **чек и прод бегут на разных рантаймах** — `vitest` под node, systemd под
bun, а `openReadonlySqlite` ветвится `bun:sqlite` vs `node:sqlite`. И 121 файл
в `scripts/` жёстко ссылается на `src/gateway` / `src/core`.

### 5.2. Правило kernel (перечислимое, не «нужно ≥2 срезам»)

Формулировка «нужно ≥2 срезам» дословно пропускает `http-utils` — он нужен
двадцати. Правило заменяется на:

1. **Allowlist модулей прямо в тесте.** Не в списке — не в kernel.
2. **Запреты по содержимому:** в kernel нет SQL, нет `node:http`, нет `spawn`.
3. `kernel` не импортирует `features` и `adapters` — как было.

### 5.3. Порядок фаз

| Фаза | Содержание                                                                                       | Проверка                                                     |
| ---- | ------------------------------------------------------------------------------------------------ | ------------------------------------------------------------ |
| 0    | Тест направления импортов + список нарушений + **инвентарь путей-от-файла** + карта «файл → срез» | тест краснеет на новом нарушении; инвентарь покрывает 10 файлов |
| 1    | **H:** один владеющий тип результата; реестры вместо литеральных списков; контракты стадий       | новое поле результата = 1 файл (замер до/после)              |
| 2    | **C:** владелец каждой таблицы; SQL мимо порта — только в `stores`; распил `http-utils`          | ни одного SQL вне репозиториев; циклов меньше на N           |
| 3    | **B, опционально:** пилот на `capture` (лист: 3 внешних зависимости против 12+5 у `apply`)       | поведение байт-в-байт, те же тесты зелёные                   |

**Гейт каждой фазы** (расширен — старого «vitest + tsc + curl» мало):

```console

npx tsc --noEmit -p tsconfig.check.json         # exit 0
bun -e 'import("./src/gateway/server.ts")'      # прод-рантайм, не node
npx tsx scripts/tz09-probe/f4b-critic-gate.mts  # пробы, а не только юниты
systemctl --user restart tdai-gateway && curl -s localhost:8420/health
```

**Самостоятельный чек фазы 0:** `npx vitest run src/architecture.test.ts` —
зелёный на текущем дереве; после добавления заведомо запрещённого импорта
(`kernel` → `features`) падает с именем файла и ребра.

## 6. Что НЕ делаем

* Не трогаем `offload` (81 файл, 2 внешних импортёра).
* Не вводим порт там, где реализация одна.
* Не режем на npm-воркспейсы, пока не убраны циклы.
* Не меняем схему БД и внешние контракты (`/memory/*`, MCP, `role.json`).
* Не двигаем файлы из §5.1 до инвентаря путей.
