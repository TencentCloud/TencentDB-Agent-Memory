# TZ-05: scopes и provenance поверх существующего стора (Phase 5)

> Источник: [requirements-memory-agents-draft.md](../requirements-memory-agents-draft.md) §10, таблица A/D, фаза 5
> Модель: [agent-architecture.md](../agent-architecture.md) — §3.6 (границы), §4.5 (точка коммита), §6 (что не делаем)
> Факт-чек кода: 2026-08-10

## Контекст

Три предпосылки пакета не выдержали проверки кодом:

- Таблицы `structured_memory` **нет**. Носитель L1 — `l1_records`.
- Колонки для scope **уже существуют**: `project_id TEXT DEFAULT ''` и `scope TEXT DEFAULT 'global'` добавляются миграцией (`src/core/store/sqlite.ts:666-667`), индекс `idx_l1_scope_project` — там же (`:679`).
- **Фильтрация по scope тоже уже атрибутная — предпосылка первой редакции пакета была ложной.** Никакого «текстового матча» в пути recall нет: `passesScope` (`src/core/hooks/auto-recall/scope.ts:29-38`) сравнивает поля `r.scope` и `r.project_id`, и применяется во всех четырёх стратегиях — keyword (`search-keyword.ts:28`), hybrid (`search-hybrid.ts:95,137`), embedding (`search-embedding.ts:36`), общий путь (`search.ts:91`). На уровне SQL предикат тоже атрибутный: `AND (?2 = '' OR ?2 = '__decay_all__' OR COALESCE(r.scope,'') <> 'project' OR r.project_id = ?2)` (`sqlite.ts:929`). Запись атрибута работает: `l1-extraction-messages.ts:72` проставляет `scope: "project"`, `l1-writer.ts:245` пишет через `resolveScope`.

  Следствие: критерии «чужой проект не просачивается» и «в recall нет фильтрации по подстроке» **проходят без единой строки нового кода — но только на дефолтном режиме `hidden`**. Как приёмка в таком виде они бесполезны, а как мотивировка вредны: исполнитель пойдёт чинить работающий фильтр.

  На боевом конфиге картина обратная. `tdai-gateway.yaml:43` ставит `crossProject: decay`, а `scope.ts:34` — это `if (mode === "decay") return true` до всех остальных проверок: в задеплоенном режиме фильтр по проекту **не применяется вообще**, чужие записи проходят намеренно и штрафуются только весом (`crossProjectDecay: 0.5`, `:44`). Поэтому критерий 1 обязан прогоняться на обоих режимах и формулироваться раздельно: на `hidden` чужой проект не возвращается, на `decay` — возвращается, но ранжируется ниже своего при прочих равных. Прогон на одном `hidden` — это проверка режима, в котором система не работает.
- **Настоящая незакрытая часть — дефолт.** В `passesScope` строка `if (r.scope !== "project") return true` означает, что запись с непроставленным scope проходит **как глобальная**. Вот это и есть невыполненное требование (критерий 2), и оно не имеет отношения к подстрокам. Второе, что остаётся настоящей работой, — provenance, которого нет вовсе.
- Отдельно, чтобы не путать с фильтрацией: индекс `idx_l1_scope_project` не обязательно берётся планировщиком — предикат на `:929` собран через цепочку `OR` и в таком виде не SARGable. Если пакет хочет «чтобы индекс заработал по назначению», формулировать надо именно так, а не «убрать текстовый матч».
- `MemoryClient` дублирует уже существующий backend-agnostic интерфейс `IMemoryStore` (`src/core/store/types.ts`) с двумя реализациями. Второй клиент поверх него — лишний слой (§6 модели).

Плюс два уточнения по границам:

- **D1 идёт через gateway HTTP `/memory/*`** (`src/gateway/memory-routes.ts`, `memory-routes/`) и `src/gateway/memory-tools.ts`, а **не** через `HostAdapter`: в его контракте памяти нет вовсе (`src/core/types.ts:154-166` — только `getRuntimeContext` / `getLogger` / `getLLMRunnerFactory`).
- **EventBus не вводится.** Точка расширения одна — `MemoryCommitObserver` из tz-03. Универсальная шина без второго названного подписчика — спекулятивная абстракция (§6 модели).

## Цель

Сделать scope формальным атрибутом записи с provenance, не заводя параллельных абстракций.

## Ожидаемый результат

- Запись L1 несёт scope как данные, а не как совпадение подстроки, и цепочку происхождения.
- Recall фильтрует по атрибуту (`idx_l1_scope_project` начинает работать по назначению).
- Носитель scope/provenance для L2 и L3 назван явно — файлы сцен и профиль, а не «тоже колонка».

## Scope

**Входит:**

- Заполнение и использование существующих `scope` / `project_id`. Не «вместо текстового матча» — матча никогда не было, сравнение атрибутное с самого начала (`scope.ts:29-38`). Закрывается конкретное: дефолт `scope !== "project" → пропустить` (`scope.ts:36`) и поведение на боевом `crossProject: decay`.
- `provenance` — происхождение записи: источник, цепочка действий, время. Носитель выбирается явно и одинаково работает на обоих бэкендах.
- Носитель scope/provenance для L2 (front-matter файла сцены плюс `scene_index`) и L3 (профиль) — назван, а не подразумевается.
- Запись атрибутов идёт через точку коммита tz-03, а не отдельным путём.

**Не входит:**

- `MemoryClient` — используется `IMemoryStore`.
- `EventBus` — используется `MemoryCommitObserver`.
- Создание колонок `scope_*` под каждый уровень: иерархия выражается парой (`scope`, `project_id`) плюс provenance, а не четырьмя колонками.

**Инварианты пакета:**

| Инвариант | Проверка |
|---|---|
| `scope-filter-enforced` | `[t]` recall с `scope=project` не возвращает записи другого проекта при совпадающем тексте; запись без scope не просачивается как global |
| `backend-parity` | `[t]` scope и provenance читаются и пишутся на обоих бэкендах; отличия — только из списка деградаций |
| `counters-match-store` (наследуется из tz-03) | `[t]` запись атрибутов идёт через точку коммита и не расходится со счётчиками |

## Зависимости

Предшественники — tz-01 (контракт) и tz-03 (точка коммита). От tz-06 и tz-07 не зависит. tz-04 после этого пакета может ввести веса по scope (сейчас `deferred`).

## Требования (функциональные)

- **A3 (F5)**: provenance каждой записи: источник (`user-input` / `role-run` / `manual` / `import`), цепочка `{роль, действие, время}`, время создания. Записывается ролью через apply, а не постфактум.
- **A4 (F5)**: scope — атрибут. Текстовый матч из пути recall убирается. Записи без scope получают явное значение при миграции, а не остаются пустыми.
- **A4a (решено)**: носитель для L2 — front-matter файла сцены и запись в `scene_index`; для L3 — профиль; **для L1 — зарезервированный ключ `_tdai_provenance` внутри существующего `metadata_json`**. Новых колонок и таблиц под provenance не заводится.

  Обоснование: `metadata_json` уже сквозной через `IMemoryStore` — объявлен в общем типе (`src/core/store/types.ts:50,71,100`), есть в SQLite (`sqlite.ts:643-657`) и на TCVDB, где пишется при upsert (`tcvdb.ts:427,472`) и читается при выдаче (`:605`, `:1201`). Отдельная колонка потребовала бы миграции на обоих бэкендах ради того же неиндексируемого JSON; отдельная таблица немедленно ломает `backend-parity`, потому что на TCVDB таблиц в этом смысле нет. Запрашивать provenance фильтром пакет не требует — только записать и прочитать обратно (A3, критерий 3), а запрашиваемая часть (scope, project_id) уже вынесена в настоящие колонки с индексом.
- **A4b (владение namespace)**: ключ `_tdai_provenance` принадлежит ядру. Значение, пришедшее из вывода модели, из HTTP-входа или из импорта, отбрасывается и не может подменить серверную цепочку. На создание записи ядро формирует provenance; на обновление и merge — сначала читает существующий ключ, затем добавляет шаг. **Полная замена `metadata_json` без сохранения зарезервированного ключа запрещена.**

  Это не теоретическая осторожность: оба бэкенда заменяют метаданные целиком (`sqlite.ts:719` — `metadata_json=excluded.metadata_json`; `tcvdb.ts:427` — `JSON.stringify(record.metadata)`), а штатный путь извлечения передаёт входящие метаданные напрямую (`src/core/record/l1-extraction-store.ts:45` → `src/core/record/l1-writer.ts:235`, `metadata: memory.metadata`) без слияния с существующими. Apply-пути (merge, rewriteRecord) старый объект сохраняют, а обычное near-dup обновление — нет, и именно оно сотрёт цепочку.
- **A4c (форма схлопывания, решено числом)**: цепочка хранит **последние 20 шагов**. Шаг — `{role, action, at}`, порядка 60–80 байт, поэтому полная цепочка укладывается в ~1.5 КБ внутри `metadata_json` и не конкурирует с содержимым записи.

  При переполнении самые старые шаги сворачиваются в **одну** запись вида `{collapsed: <сколько свёрнуто>, from: <время первого>, to: <время последнего>}`, которая занимает место одного шага и всегда стоит первой. Схлопывание обязано быть видимым: «было 24 шага, стало 20» читается как `collapsed: 5` плюс 19 живых, а не как молчаливая потеря первых пяти.

  Число 20 выбрано как рабочее, а не выстраданное: цепочка длиннее двадцати шагов на одной записи означает, что запись перекраивают роли по кругу, и это сам по себе повод разбираться, а не хранить историю. Менять его — правкой одной константы, без миграции: старые цепочки короче лимита остаются валидными.
- **D1 (F5)**: контракт потребителя — gateway HTTP `/memory/*` и `memory-tools.ts`. Критерий: recall и запись работают по HTTP-контракту без `~/.pi` в путях. Хост-нейтральная обёртка — предмет tz-08, здесь только серверная сторона.
- **D2 (F5)**: EventBus — **deferred**. Гейт на пересмотр: два названных подписчика, которых не покрывает `MemoryCommitObserver`. Пока их нет, требование закрыто портом из tz-03.

## Критерии приёмки

1. `[t]` Recall с `scope=project` и записью другого проекта, текстуально совпадающей с запросом, прогоняется **на обоих режимах**: при `crossProject: hidden` чужая запись не возвращается; при `crossProject: decay` (боевой конфиг, `tdai-gateway.yaml:43`) — возвращается, но стоит ниже своей записи с сопоставимым скором. Прогон только на `hidden` критерий не закрывает.
2. `[t]` Запись без scope не участвует в выдаче как global.
3. `[t]` Provenance сохраняется полностью на цепочке из трёх шагов и читается обратно.
3a. `[t]` Обычное извлечение с near-dup обновлением той же записи **не теряет** предыдущие шаги (регрессия на `l1-writer.ts:235`).
3b. `[t]` Входные метаданные с поддельным `_tdai_provenance` не подменяют серверную цепочку.
3c. `[a]` Под provenance не заведено ни новой колонки, ни новой таблицы.
4. `[t]` Scope и provenance читаются и пишутся на обоих бэкендах (contract-тест `IMemoryStore`).
5. `[t]` Запись с пустым или неизвестным `scope` не выдаётся за global: сегодня `scope.ts:36` (`if (r.scope !== "project") return true`) пропускает её при любом `projectId`. Критерий закрыт, когда legacy-запись без `scope` перестаёт молча проходить фильтр проекта, а её трактовка задана явно, а не через отрицание. Прежняя формулировка («в пути recall нет фильтрации по подстроке») выполнялась и до пакета — как приёмка она пустая.
6. `[t]` Запись по HTTP-контракту `/memory/*` работает без `~/.pi` в путях.
7. `[a]` В репозитории нет второго клиента памяти поверх `IMemoryStore` и нет EventBus. **Регрессионный сторож, не приёмка** — выполняется сегодня по устройству системы. Ловит одно: попытку протащить provenance через новый слой вместо `metadata_json`. В отчёте о готовности пакета не засчитывается.

## План

1. Реализовать носитель по A4a (`metadata_json._tdai_provenance` для L1, front-matter + `scene_index` для L2, профиль для L3) и слияние-при-обновлении по A4b. Отдельно: функция `writeProvenanceRecord` (`src/gateway/apply-executor/apply-provenance.ts:18`) вопреки имени provenance не пишет — это лишь обёртка над `writeMemory`, сохраняющая `created_time`. Имя вводит в заблуждение и должно быть исправлено в этом же пакете, иначе следующий читатель решит, что путь уже закрыт.
2. Заполнить `scope`/`project_id` на записи через apply; миграция существующих записей отдельным шагом.
3. Перевести recall с текстового матча на атрибут.
4. Contract-тест на обоих бэкендах.
5. Проверить HTTP-контракт потребителя без pi-путей.

## Самостоятельная проверка (не тестами исполнителя)

**S1. Чужой проект не просачивается.**
Создать в двух проектах записи с намеренно одинаковым текстом. Сделать recall в первом.
→ Возвращается только своя; чужая не приходит, несмотря на полное текстовое совпадение.
Это прямая проверка перехода с текстового матча на атрибут: до правки совпадающий текст притянет чужую запись.

**S2. Запись без scope не притворяется общей.**
Взять запись, у которой scope не проставлен.
→ Она не участвует в выдаче как global.
Фальсификация: проставить этой же записи корректный scope текущего проекта — она обязана появиться в выдаче. Если не появилась, фильтр режет не по атрибуту, а по чему-то ещё, и первая половина наблюдения ничего не доказывала.

**S3. Происхождение читается обратно.**
Провести запись через цепочку из трёх шагов (создание → изменение ролью → слияние).
→ В provenance видны все три шага с ролями и временем; цепочка не обрезана до последнего.
Фальсификация: провести четвёртый шаг и убедиться, что он добавился, а первый не исчез молча. Если цепочка ограничена по длине (см. R2), схлопывание старых шагов обязано быть видимым — «было 4 шага, стало 3 плюс отметка о схлопывании», а не тихая потеря.

**S4. Работает на обоих бэкендах.**
Прогнать сценарии S1–S3 на SQLite и на TCVDB-заглушке.
→ Результат одинаков либо расхождение перечислено в списке деградаций.
Фальсификация: намеренно записать scope только на одном бэкенде (сломать запись на втором) — сценарий S1 обязан упасть именно на нём. Если оба «зелёные» при заведомо сломанном втором, прогон на втором бэкенде фиктивен.

**S5. Миграция scope не сломала существующее.**
До миграции снять распределение записей по scope, после — снова.
→ Ни одна запись не потеряна, ни одна не сменила проект. Значение по умолчанию выбрано по отчёту dry-run, а не назначено заранее.

## Нефункциональные

- Фильтр по scope использует существующий индекс, а не полный скан.
- Миграция существующих записей идемпотентна и переигрываема.

## Риски

- **R1 (high)**: миграция scope у существующих записей необратима по смыслу (пустое → конкретное). План: сначала dry-run с отчётом распределения, значение по умолчанию выбирается по отчёту, а не заранее.
- **R2 (medium)**: provenance раздувает запись. План: предел длины и формат схлопывания фиксируются числом до реализации (A4c), схлопывание видимо в самой цепочке.
- **R2a (high)**: зарезервированный ключ живёт в общей свалке `metadata_json`, которую штатный путь записи заменяет целиком (`l1-writer.ts:235`). План: слияние-при-обновлении (A4b) и регрессионный тест 3a — без них цепочка будет молча теряться на обычном извлечении, а не на редком apply.
- **R3 (medium)**: переход recall на атрибут может сузить выдачу там, где текстовый матч случайно помогал. План: прогон probe-корпуса tz-04 до и после.

## Risk tier

**Tier-3 (schema)**: миграция данных существующих записей. Отдельным PR, с dry-run и планом отката, не в одном коммите с фичей.

## Откат

- Фильтрация по атрибуту — за флагом; откат возвращает прежний путь.
- Provenance аддитивен: чтение старых записей без него не ломается.
- Миграция scope — с сохранением исходного значения до конца окна отката.

## Глоссарий

- **Scope** — пара (`scope`, `project_id`) на записи; атрибут, а не подстрока.
- **Provenance** — источник и цепочка действий, приведших к записи.
- **Точка коммита** — `MemoryCommitObserver` из tz-03; единственный путь, через который атрибуты попадают в стор.
