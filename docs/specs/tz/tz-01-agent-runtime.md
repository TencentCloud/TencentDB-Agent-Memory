# TZ-01: контракт роли управляет исполнением (Phase 1)

> Источник: [requirements-memory-agents-draft.md](../requirements-memory-agents-draft.md) §10, таблица B, фаза 1
> Модель: [agent-architecture.md](../agent-architecture.md) — §3.1 (сущности), §3.3 (роль как расширение), §5 (инварианты), §8 (порядок миграции)
> Факт-чек кода: 2026-08-10

## Контекст

Контракт роли сегодня **декоративен**: поля в `role.json` есть, исполнение идёт мимо них. Проверено чтением:

| Поле | Реально |
|---|---|
| `prompt_file` | игнорируется, путь идёт `prompt-builder.ts:94` → `role-dir-loader.ts:34-36` |
| `tools_subset` | копируется весь каталог тулов (`keeper-tools.ts:55`) |
| `model` / `thinking` | берутся глобальные `config.memory.consolidation.*` (`runner-helpers.ts:75-80`) |
| `critic_role` | ядром не вызывается, после caps сразу apply (`runner.ts:47-50`) |
| `ops_subset` | `assertOpsSubset` определён (`apply-executor/validate.ts:44`), но в `apply()` не вызывается (`apply-executor.ts:84-95`) |
| `schedule` / `threshold` | таймер берёт `config.memory.nightRun.*` (`server.ts:181-188`) |

Диспетчеризации по контракту нет: выбор раннера — сравнением имени с `"night-keeper"` (`orchestrator.ts:143`), таймер знает только эту роль (`night-run.ts:106`), `dedup-daily` (`schedule: "03:00"`) не вызывает никто, `listRoles` (`role-loader.ts:90`) используется только для HTTP-листинга (`server.ts:77,680`).

Пока это не исправлено, остальные пакеты строятся на песке: любой их параметр так же не доедет до исполнения.

## Цель

Сделать контракт роли единственным источником параметров исполнения, а диспетчеризацию — производной от контракта, а не от имени роли.

## Ожидаемый результат

- Каждое поле legacy `role.json` доезжает до synthetic package/instance, а затем до спавна и apply. После создания `ResolvedRoleContract` глобальный конфиг больше не читается.
- Выбор стратегии — по `batching.strategy` и `trigger`/`schedule`/`threshold` из контракта, без сравнения имён.
- Решение о запуске принимается по per-role `lastRunAt` (`checkpoint.ts:26-50` — уже хранится, надо начать использовать), а не по глобальному `getLastRunAt`.
- `dedup-daily` становится вызываемой ролью (запуск — отдельным решением в tz-05-ном порядке, см. §8 шаг 15 модели).

## Scope

**Входит:**

- Резолв контракта: `prompt_file`, `tools_subset`, `model`/`thinking`, `timeout_min`/`max_run_ms`, `caps`, `ops_subset`, `critic_role`.
- Диспетчер по `trigger` / `schedule` / `threshold` + per-role `lastRunAt` вместо глобального `getLastRunAt` (`server.ts:188`).
- `batching.strategy` как явный enum контракта: `fresh-tail-single-batch` (day) и `bounded-full-store-chunked` (night). Это **разная семантика**, а не разное время суток.
- Per-role single-flight (сам гейт уже есть — `role-gate.ts:25`; здесь он становится частью резолва, а не побочным эффектом).

**Не входит (осознанно):**

- Переезд в `src/agents/` — см. «Roadmap».
- **Протокол прогона и безопасность apply — tz-09**: `RoleRun` / `LaunchAttempt`, состояния, claim/lease/fence, `contract-snapshot-pinned`, вызов `assertOpsSubset` и caps, стадия критика с fail-closed. tz-01 только **резолвит** соответствующие поля контракта (`caps`, `ops_subset`, `critic_role`) и передаёт их дальше; кто и когда их применяет — предмет tz-09.
- Смена хоста — tz-06; корни путей — tz-07.

**Инварианты пакета** (полные формулировки и проверки — §5 модели):

| Инвариант | Проверка |
|---|---|
| `contract-drives-execution` | `[a]` в резолвере и стратегиях нет обращений к `config.memory.consolidation.*` / `config.memory.nightRun.*`; `[t]` две роли с разными `model` в одном прогоне получают разные binding |
| `single-writer-per-role` | `[t]` **два процесса gateway на одном `dataDir`** стартуют роль одновременно → ровно один получает lease, второй ждёт; две **разные** роли не блокируют друг друга |
| `fail-closed-role` | `[t]` битый JSON, неизвестное поле, отсутствующий промпт → роль в `disabled` с причиной, а не тихий `null` (`role-loader.ts:27`, тот же паттерн `:66-73`) |

## Зависимости

Корневой пакет, предшественников нет. От него зависят tz-02, tz-03, tz-06, tz-07 (нужен резолв контракта); tz-05 — после tz-01 и tz-03.

## Требования (функциональные)

- **B1**: резолв контракта — единая функция, возвращающая полный набор параметров прогона; ни один потребитель не читает `role.json` в обход неё.
- **B2 (F1)**: `batching.strategy` выбирает стратегию. Сравнение имени роли (`orchestrator.ts:143`) удаляется.
- **B3 (F1)**: source-of-truth имеет три уровня: portable `RolePackage`, instance-конфиг и immutable snapshot в `RoleRun`. `launcher/provider/model/thinking/auth/isolation` принадлежат обязательному instance `ExecutionBinding`, а не package. Только `LegacyRoleAdapter` может на переходном пути собрать отсутствующее legacy-значение из старого global config и обязан записать warning; V2 package/instance при отсутствии обязательного значения fail-closed. После создания Run fallback запрещён.
- **B4**: схема контракта — существующий `validateRoleConfig` (`role-schema.ts:52`); поля добавляются по правилу ниже, `REQUIRED_ROLE_FIELDS` (`role-schema.ts:39-45`) содержит **20** имён (комментарий в коде «19» неверен): `name, model, prompt_file, enabled, thinking, timeout_min, scope, trigger, schedule, threshold, idsOnly, diff_cap, diff_byte_cap, ops_subset, tools_subset, caps, max_run_ms, fail_on_missing_prompt, critic_role, runtime`.

  Добавляется одно поле — **бюджет ретраев роли**. Владельца у него сегодня нет: tz-09 (`:88`) объявляет его «полем контракта, резолвится в tz-01» и строит на нём терминальность Run (исчерпание бюджета → `failed-terminal`), но ни в `REQUIRED_ROLE_FIELDS`, ни в §3.3 модели, ни в Scope этого пакета его не было. Без него терминальное состояние tz-09 не вычислимо: Run не отличит «попытка упала, пробуем ещё» от «попыток больше нет». Поле конечно и обязательно, дефолт задаётся в схеме — бесконечный ретрай по умолчанию не подразумевается.
- **B5**: launcher, провайдер и модель роли **фиксированы** и резолвятся в `ExecutionBinding`, пиннутый в `RoleRun.binding` на момент создания прогона (§3.3–3.4 модели). Дефолта «выбери сам» нет. Поля `model`/`thinking` нынешнего `role.json` LegacyRoleAdapter переводит в instance binding; `launcherId: "pi"` добавляется там же как явно версионированная legacy-совместимость, а не как поле переносимого контракта. Сегодня эти значения до спавна не доезжают (`runner-helpers.ts:75-80`) — это и чинится.
- **B6**: per-role `lastRunAt` (`checkpoint.ts:26-50`) — источник для `ranToday`; глобальный `getLastRunAt` из решения о запуске уходит.
- **B7 (критик ролей)**: `critic_role` резолвится и пробрасывается; вызов стадии и fail-closed гейт — **tz-09**, не здесь. Сегодня поле только парсится (`role-loader.ts:113`, `role-runtime.ts:121`), а `dedup-daily-critic` не имеет `role.json`.

**Правило добавления полей.** Ключи внутри `runtime` жёстко whitelisted (`role-schema.ts:85-91`: только `extension_path` / `skill_path` / `scratch_root`, только `typeof === "string"`). Новое поле внутри `runtime` требует правки этого whitelist; массив (например `tools`) требует отдельного тип-чека — string-only проверка его отбросит. Верхнеуровневое поле добавляется в `REQUIRED_ROLE_FIELDS` вместе с guard'ом.

## Судьба файлов

Не «удалить», а перенести и проверить: часть логики, которую пакет обязан сохранить, живёт именно в файлах-кандидатах на удаление.

| Файл | Что делаем | Почему |
|---|---|---|
| `night-run.ts` | **унифицировать** | таймер, `ranToday` и catch-up остаются; уходит хардкод единственной роли (`:106`) |
| `day-runner.ts` | слить в единый раннер, удалить **после** переноса | несёт fresh-tail стратегию (`:50-60`) и удаление scratch (`:119`) |
| `night-runner.ts` | слить в единый раннер, удалить **после** переноса | несёт bounded-chunked стратегию, anchored-курсор (`:86-93`), удаление scratch (`:112`) |
| `orchestrator.ts:143` | заменить сравнение имени на выбор по `batching.strategy` | это и есть name-based dispatch |
| `role-gate.ts` | сохранить как есть | per-role single-flight (`:25`) — уже правильно |

`test ! -f` применяется только к строкам со статусом «удалить», и только после зелёных тестов переноса.

## Критерии приёмки

Проверки — исполняемые. Grep допустим только для `[a]`-чеков по исходникам, и только с явным списком исключений.

1. `[t]` Роль с `model: X` и роль с `model: Y` в одном прогоне уходят в спавн с разными моделями; ни один спавн не берёт `config.memory.consolidation.model`.
2. `[t]` Роль с `prompt_file: <путь>` получает промпт по указанному пути; при отсутствии файла и `fail_on_missing_prompt: true` — роль `disabled` с причиной, а не fallback.
3. `[t]` Роль с `tools_subset: [a]` получает ровно один тул, а не весь каталог.
4. `[t]` Резолв отдаёт `caps`, `ops_subset` и `critic_role` роли потребителю в неизменном виде (само применение проверяется в tz-09).
5. `[t]` Два прогона одной роли внахлёст → второй не стартует; две разные роли идут параллельно. Тест обязан гонять **два процесса gateway на одном `dataDir`**, а не два вызова внутри одного: сегодня координация живёт в памяти процесса (`role-gate.ts:25`), поэтому внутрипроцессный тест зелёный и на сломанной межпроцессной блокировке. Модель требует ровно этого (`agent-architecture.md:287`, `:315` — «тест обязан гонять два процесса, а не один»).
6. `[t]` `dedup-daily` вызывается диспетчером по своему `schedule`, а не остаётся мёртвым контрактом.
7. `[a]` Вне резолвера контракта нет чтения `config.memory.consolidation.*` и `config.memory.nightRun.*` для параметров роли. Исключения: `src/config.ts`, тесты.
8. `[a]` Нет сравнения имени роли для выбора ветки исполнения: `grep -rnE '"(night-keeper|memory-keeper|dedup-daily)"' src/gateway/consolidation/ --include='*.ts' | grep -v '\.test\.ts'` → только регистрация/логи, ни одного `if`/тернарника выбора раннера.
9. `[t]` Единственный `LegacyRoleAdapter` преобразует полный текущий `role.json` вместе с `runtime.extension_path`/`skill_path` в synthetic package + instance + assets. Characterization фиксирует текущий argv/prompt/tools; parity-shadow generic bundle совпадает с legacy по digest до отключения адаптера.

## План

1. Резолвер контракта: одна точка, полный набор параметров, `ExecutionBinding` с фиксированными launcher, провайдером и моделью.
1a. Реализовать единый `LegacyRoleAdapter` — владелец tz-01. Он адаптирует формат, binding и executable assets; pi-launcher только исполняет уже resolved legacy assets. До миграции снять characterization argv/prompt/tools и добавить parity-shadow.
2. Пробросить резолв в спавн (`runner-helpers.ts:75-80`, `keeper-run.ts:27-40`) и в тулы (`keeper-tools.ts:55`).
3. `batching.strategy` вместо сравнения имени (`orchestrator.ts:143`).
4. Диспетчер по `trigger`/`schedule`/`threshold` + per-role `lastRunAt`; глобальный `getLastRunAt` уходит из решения о запуске.
5. `fail-closed-role`: `role-loader.ts:27` и `:66-73` возвращают причину вместо `null`.
6. Перенос стратегий в единый раннер, удаление `day-runner.ts`/`night-runner.ts` по таблице выше.

## Самостоятельная проверка (не тестами исполнителя)

Критерии выше проверяются тестами, которые пишет тот же, кто пишет код, — их можно подогнать. Ниже — независимые наблюдения на **живом** пайплайне. Каждая точка: что сделать → что должно быть видно → чем доказать, что проверка не врёт.

**S1. Роль реально идёт на своей модели.**
Поставить в `role.json` двух ролей заведомо разные модели, запустить обе, посмотреть в лог спавна и в Run-репозиторий фактические аргументы дочернего процесса.
→ Видно две разные модели, и ни одна не равна `config.memory.consolidation.model`.
Фальсификация: временно поменять модель в глобальном конфиге на третье значение — в аргументах ничего не должно измениться. Если изменилось, контракт по-прежнему декоративен.

**S2. Промпт берётся по `prompt_file`.**
Указать в контракте путь к промпту с уникальным маркером в тексте, запустить роль, найти маркер в сохранённом промпте прогона.
→ Маркер на месте.
Фальсификация: удалить файл и выставить `fail_on_missing_prompt: true` — роль обязана уйти в `disabled` с причиной, а не молча подставить canonical-путь.

**S3. `dedup-daily` ожил.**
Дождаться его `schedule` (или сдвинуть время) и посмотреть секцию «Last runs» в `memory_health.md` — этот дашборд пишется после каждого не-dry прогона уже сегодня, поэтому наблюдение доступно **до** tz-09 и не требует Run-репозитория.
→ В «Last runs» появилась строка `dedup-daily`; рядом лежит отчёт прогона.
Контроль «до»: сегодня эту роль не вызывает никто, поэтому строки нет и быть не может.
Фальсификация: выставить роли `enabled: false` — строка обязана перестать появляться. Если появляется, диспетчер игнорирует контракт в обе стороны.

**S4. Диспетчер не знает имён.**
Добавить в каталог ролей четвёртую роль с новым именем и корректным контрактом.
→ Она подхватывается и исполняется без единой правки кода.
Это главная проверка пакета: если новая роль требует правки `orchestrator.ts`, диспетчеризация осталась name-based.

**S5. Битый пакет роли не исчезает молча.**
Испортить JSON одной роли.
→ В листинге ролей она присутствует со статусом `disabled` и причиной; gateway жив; остальные роли работают.
Фальсификация: сегодня такая роль просто пропадает из выдачи (`role-loader.ts:27`).

## Нефункциональные

- Резолв контракта ≤ 5 мс (кэш с инвалидацией по mtime).
- Отказ резолва — `disabled` с причиной в листинге ролей, не падение gateway.
- Параллельность: разные роли независимы; одна роль — строго последовательно (`role-gate.ts:25`).

## Риски

- **R1 (high)**: включение caps-гейта fail-closed может остановить боевой keeper на кандидате, который раньше проходил. План: shadow-режим с логом расхождений, включение после суток без расхождений.
- **R2 (medium)**: перенос стратегий day/night — место, где легко потерять anchored-курсор. План: characterization-тесты обеих стратегий **до** переноса (§8 шаг 1 модели).
- **R3 (medium)**: `dedup-daily` оживает и начинает удалять. План: dry-run с parity-сверкой, живое расписание — отдельным решением.

## Risk tier

**Tier-2** (диспетчеризация и резолв параметров), с переходом в **Tier-3** на пункте 3 плана: caps-гейт стоит на пути мутаций памяти.

## Откат

- Резолв и диспетчер — за feature-флагом, откат возвращает name-based ветку.
- caps-гейт откатывается в shadow-режим без потери данных.
- Удаление раннеров — последним шагом, после зелёных тестов; до этого оба пути живы.

## Roadmap (вне пакета)

Переезд пайплайна в `src/agents/` — структурная перекладка без поведенческого эффекта. Делать после того, как контракт заработает: иначе переносится текущая неверная семантика. Критериев приёмки в этом пакете не имеет.

## Глоссарий

- **Контракт роли** — `role.json`, валидируемый `validateRoleConfig`; 20 верхнеуровневых полей.
- **ExecutionBinding** — instance-конфигурация `launcherId/provider/model/thinking/authProfileRef/isolationProfileRef`, целиком пиннутая в прогон.
- **LegacyRoleAdapter** — единственный переходный адаптер нынешнего `role.json`, включая binding и `extension_path`/`skill_path`; отдельного executable-адаптера нет.
- **Batching strategy** — именованная стратегия сборки workset: `fresh-tail-single-batch` или `bounded-full-store-chunked`.
- **Single-flight per role** — взаимное исключение по ключу роли, не по сессии.
