# TZ-02: keeper — единственный писатель сцен + scratch из instance-конфига (Phase 2)

> Источник: [requirements-memory-agents-draft.md](../requirements-memory-agents-draft.md) §10, таблица A, фаза 2
> Модель: [agent-architecture.md](../agent-architecture.md) — §3.5 (рабочая папка), §5 (`single-scene-writer`)
> Факт-чек кода и диска: 2026-08-10

## Контекст

**Исходная посылка пакета была неверна.** Проверено на диске и в коде:

- L2 **не отключена**: в `scene_blocks/<projectSlug>/` лежит **31** `.md`-файл. Сцены пишет `memory-keeper` операцией `rewriteBlock` через `POST /memory/apply`.
- Таблицы `scenes` **не существует**. L2 — это markdown-файлы плюс индекс `.metadata/scene_index/<slug>.json`, а не строки в БД.
- No-op в inline-L2 (`utils/pipeline-factory/l2-runner.ts:29-33`) — **намеренный single-writer gate**, а не поломка: при `consolidation.enabled` inline-путь отключается, потому что сцены принадлежат keeper'у. Снимать его нельзя, это и есть защита.

Что действительно сломано:

- Гейт выключает только **inline**-путь. Гарантии одного писателя нет: `memory-keeper` и `night-keeper` имеют разные ключи single-flight (`role-gate.ts:25` — по роли) и **оба** несут `rewriteBlock` в `ops_subset`. Две роли могут переписать один блок одновременно.
- `scratch_root` **уже заполнен** во всех трёх `role.json` (`.../runs/<role>`), но оркестратор его игнорирует и хардкодит корень: `server.ts:171-174`, `join(dirname(dataDir), "tdai-memory-keeper")`.
- Scratch удаляется после не-dry-run прогона (`day-runner.ts:119`, `night-runner.ts:112`) — разобрать прогон постфактум нечем.

## Цель

Сделать одного писателя сцен механическим фактом, а не соглашением; scratch-корень брать из instance-конфига роли.

## Ожидаемый результат

- Конфликтующая запись в один scene-блок невозможна: вторая роль получает отказ, а не перетирает файл.
- `scratchRoot` резолвится из instance-поля, в которое `LegacyRoleAdapter` переводит текущий `runtime.scratch_root`; хардкод в `server.ts:171-174` уходит.
- Артефакты прогона переживают прогон настолько, насколько задано retention (`keep_scratch`), а не удаляются безусловно.

## Scope

**Входит:**

- Ключ single-flight для сцен — по **ресурсу** (scene-блок / проектный слаг), а не по роли.
- Резолв `scratchRoot` из instance-конфига. На переходном пути `LegacyRoleAdapter` переводит туда `runtime.scratch_root`; дефолт — прежнее место, чтобы не ломать существующие прогоны.
- Аддитивное instance-поле `keep_scratch` (с legacy-разбором по правилу добавления полей из tz-01) + retention вместо безусловного удаления.
- Раскладка папки прогона по §3.5 модели: `input/workset.json`, `out/result.json`, `out/critic.json`, `prompt/`, `artifacts/`.
- **Разведение входа и выхода.** Сегодня это один файл `diff.json`: вход пишется туда (`runner-stages.ts:68-78`), результат читается оттуда же (`:121`). Переход обязан быть lockstep, потому что имя зашито в промптах: **45 упоминаний в 6 файлах** `src/core/prompts/skills/*/SKILL.md` (memory-keeper 8, night-keeper 9, dedup-daily 12, memory-critic 4, night-critic 5, dedup-daily-critic 7), которые ещё и зеркалятся наружу через `scripts/sync-memory-skills.sh`. Последовательность: сначала дублировать вход в новое место, сохранив `diff.json`; затем править SKILL.md и прогнать sync; только потом убирать legacy-путь. Обратное чтение (fallback) живёт до конца окна отката.

**Не входит:**

- Снятие inline-гейта `l2-runner.ts:29-33` — он остаётся.
- Введение таблицы `scenes` — L2 остаётся файловой.
- Смена модели роли: провайдер и модель принадлежат обязательному instance `ExecutionBinding` и пиннятся в `RoleRun` (tz-01 B5).

**Инварианты пакета:**

| Инвариант | Проверка |
|---|---|
| `single-scene-writer` | `[t]` две роли с `rewriteBlock` на один блок → сериализованы claim'ом `scene:<slug>`; второй проходит после ожидания и перепроверки manifest'а; итоговая запись `scene_index` соответствует последнему применённому содержимому файла |
| `single-persona-writer` (новый) | `[t]` два Run с `rewritePersona` не перекрываются; итоговый `persona.md` соответствует ровно одной verified-операции, а не смеси двух |
| `inspectable-run` (частично) | `[f]` после прогона существуют `run.json`, `input/workset.json`, `out/result.json`, `out/critic.json`; удаляются не раньше retention. **Лог сессии в этом пакете не проверяется** — сессии появляются только после снятия `--no-session` в tz-06; полная форма инварианта закрывается там |
| `contract-drives-execution` (частично) | `[t]` модель роли на пути L2 берётся из резолвнутого instance `ExecutionBinding`; хардкода модели и чтения global config после создания Run нет. Полная форма — tz-01 |

**Удалённый инвариант.** `provider-model-inheritance` («L2 использует модель основной сессии») исключён: он противоречит обязательному instance `ExecutionBinding`, пиннутому в Run (tz-01 B5, §3.4 модели). Замены новым именем не вводится — используется существующий `contract-drives-execution` из §5 модели.

## Зависимости

Предшественник — tz-01 (резолв контракта). tz-04 может использовать сцены в recall, но не блокируется этим пакетом.

**Зависимость по `inspectable-run`:** полная форма инварианта (включая лог сессии) требует снятого `--no-session`, а это tz-06. Здесь проверяется только файловая часть; сессионная закрывается в tz-06. Это единственная связь между пакетами, и она односторонняя — tz-02 не блокирует tz-06.

## Требования (функциональные)

- **A1 (F2, решено)**: обе роли **сохраняют** `rewriteBlock` и `rewritePersona`; взаимное исключение обеспечивает ядро durable-claim'ами по ресурсу. Ресурс — не отдельный файл, а связка:

  ```text
  scene:<canonical-project-slug>  = scene_blocks/<slug>/**  +  .metadata/scene_index/<slug>.json
  persona:<canonical-path>        = persona.md
  ```

  Claim берётся до мутации, удерживается через запись файла, пересборку индекса, проверку постусловия и запись receipt'а, и только потом отпускается. Claims берутся в стабильном порядке (лексикографически по ключу ресурса), чтобы два прогона с пересекающимися наборами не встали в deadlock.

  Почему связка, а не путь файла. Путь закрывает прямую гонку по содержимому — и `rewriteBlock`, и `rewritePersona` сводятся к массиву целевых путей (`apply-executor/apply-ops-rewrite.ts:66`). Но индекс пишется **отдельной, более поздней** операцией (`apply-executor.ts:104`), поэтому два apply по разным файлам одного слага могут разойтись так, что последним ляжет устаревший снимок индекса. Индекс к тому же пишется без атомарной подмены — прямой `fs.writeFile` (`src/core/scene/scene-index.ts:151`), а `SceneIndexEntry` не содержит дайджеста вовсе: только `filename`, `summary`, `heat`, `created`, `updated` (`scene-index.ts:9-15`).

  Claim обязан быть **межпроцессным**, а не in-memory: и HTTP-маршрут, и оркестрация создают свои экземпляры executor'а (`apply-executor/apply-route.ts:80`, `consolidation/runner-helpers.ts:100`), поэтому лок внутри объекта ничего не сериализует.
- **A1c (полный инвентарь писателей)**: писателей сцен и персоны не два. Кроме `ApplyExecutor` существует **целое inline-семейство**, работающее мимо apply:

  | Путь | Что делает с диском |
  |---|---|
  | `profile-sync.ts:151-155` | `rm -rf` всего каталога сцен + `rename` поверх; следом то же с `persona.md` (`:167-172`) |
  | `persona-generator.ts:190` | прямой `fs.writeFile(personaPath, …)` |
  | `filename-normalizer.ts:183` | `fs.rename(from, to)` по файлам сцен |
  | `scene-extractor.ts:147` | `backupDirectory(blocksDir, …)` (`src/utils/backup.ts:72`) |
  | `scene-extractor.ts:234` | `restoreLatestDirectory(…, blocksDir)` — пишет в каталог сцен |
  | `scene-extractor.ts:298` | вызывает нормализатор имён |

  **Все они висят на одном флаге.** `SceneExtractor` создаётся ровно в одном месте (`l2-runner.ts:88`), `PersonaGenerator` — ровно в одном (`l3-runner.ts:44`), `pullProfilesToLocal` вызывается там же (`l2-runner.ts:44-45`, `l3-runner.ts:39-40`), и оба раннера выходят раньше по гейту `isConsolidationEnabled` (`l2-runner.ts:29-33`, `l3-runner.ts:26-29`). То есть в целевой конфигурации не выполняется ни одна строка таблицы.

  Отсюда три следствия, которые пакет обязан зафиксировать:

  1. Ни сериализация apply по стору, ни claim по `scene:<slug>` это семейство **не удерживают** — оно не проходит через `ApplyExecutor` вовсе, а `profile-sync` и restore бьют по всем слагам разом.
  2. Единственное, что отделяет каталог сцен от полного перезаписывания, — **один флаг конфига, проверяемый в двух местах**. Ни один тест не проверяет, что гейт на месте; при этом инвариант `single-scene-writer` формулируется так, будто писатель один по устройству, а не по настройке.
  3. Запуск двух gateway с разными значениями флага на одном `dataDir` — конфигурация, ведущая к потере сцен. Это надо назвать запрещённой конфигурацией явно, а не полагаться на то, что так никто не сделает.

  Требование пакета: покрыть тестом недостижимость каждого пути таблицы при `consolidation.enabled`, и записать инвариант в честной форме — «один писатель **при включённой консолидации**», а не «один писатель».
- **A1a**: пересборка индекса становится точечной. Сейчас после **любого** apply, включая persona-only, перестраиваются индексы всех проектов (`apply-executor/apply-route.ts:28` → `src/core/scene/scene-index.ts:106`). При claim-модели это вынуждало бы захватывать слаги всех проектов и превращало бы механизм в глобальный лок. Синхронизируются только затронутые слаги.
- **A1b**: наблюдаемая политика конфликта — **ожидание, а не немедленный отказ**. Инвариант `single-apply-per-store` (`agent-architecture.md:288`) требует, чтобы конфликтующие apply ждали; первая редакция `single-scene-writer` (`:289`) требовала, чтобы вторая роль получала conflict. Это противоречие: две политики на одну ситуацию. Принята одна — второй ждёт освобождения claim'а, затем **обязан перепроверить manifest baseline** и получает отказ только если базовая линия сдвинулась под ним. Отказ без ожидания остаётся лишь для истёкшего lease и для превышения таймаута ожидания.
- **A2**: inline-гейт (`l2-runner.ts:29-33`) сохраняется и покрывается тестом на то, что он не снят.
- **B5 (F2)**: `scratchRoot` берётся из instance-конфига; `LegacyRoleAdapter` проецирует туда текущий `runtime.scratch_root`, а при его отсутствии использует прежний дефолт. Хардкод `server.ts:171-174` удаляется.
- **B5a**: `keep_scratch` — аддитивное instance-поле; при `true` артефакты прогона сохраняются до истечения retention, при `false` — текущее поведение.
- **A3**: если сцены давно не обновлялись, догоняющий прогон идёт **через диспетчер** (tz-01), а не через inline-путь.

## Критерии приёмки

1. `[t]` Два прогона с `rewriteBlock` на один блок сериализованы: второй ждёт, затем перепроверяет manifest и либо применяется, либо отклоняется по сдвинувшейся базовой линии. Запись в `scene_index` соответствует последнему применённому содержимому.
1a. `[t]` Два прогона с `rewriteBlock` на **разные файлы одного слага**: итоговый `scene_index` содержит обе правки. Более поздняя пересборка индекса не возвращает его к снимку, снятому до первой правки.
1b. `[t]` Два прогона с `rewritePersona`: результат равен ровно одной из двух версий, не их смеси.
1c. `[t]` После apply, затронувшего один слаг, индексы прочих проектов не переписаны (проверяется по mtime).
1d. **Согласованность файла и индекса проверяется по содержанию, а не «по дайджесту»**: `SceneIndexEntry` дайджеста не содержит (`src/core/scene/scene-index.ts:9-15`). Пакет обязан либо добавить поле дайджеста в запись индекса, либо задать правило вычисления ожидаемой записи из применённого содержимого. Формулировка «совпадают по дайджесту» без этого неоперациональна.
2. `[t]` Instance со `scratchRoot: X` пишет в `X`, а не в `join(dirname(dataDir), "tdai-memory-keeper")`; отдельный compatibility-тест доказывает проекцию legacy `runtime.scratch_root: X` в это поле.
3. `[a]` `grep -rn 'tdai-memory-keeper' src/gateway/server.ts` → 0.
4. `[f]` После прогона с `keep_scratch: true` каталог попытки существует и содержит файловые артефакты §3.5 (лог сессии — критерий tz-06).
4a. `[t]` Вход роли читается из нового места; при его отсутствии срабатывает fallback на `diff.json`.
4b. `[a]` После правки промптов ни один `SKILL.md` не ссылается на снятый путь, и `scripts/sync-memory-skills.sh` прогнан (расхождение зеркала — падение).
5. `[t]` Inline-L2 при `consolidation.enabled` по-прежнему no-op (гейт не снят).
6. `[t]` На пути L2 нет обращения к глобальной модели: роль с `model: X` уходит в спавн с `X`.

## План

1. Ввести межпроцессные durable-claims по ресурсам `scene:<slug>` и `persona:<path>` (стабильный порядок захвата, удержание до receipt'а) и точечную пересборку индекса вместо `syncSceneIndexAllProjects`.
2. Резолв `scratchRoot` из instance-конфига; в `LegacyRoleAdapter` спроецировать текущий `runtime.scratch_root`; удалить хардкод `server.ts:171-174`.
3. Добавить instance-поле `keep_scratch` и его legacy-проекцию (whitelist `role-schema.ts`, guard, дефолт `false`).
4. Разложить папку прогона по §3.5; удаление — по retention, а не безусловное (`day-runner.ts:119`, `night-runner.ts:112`).
5. Тест на неснятый inline-гейт.

## Самостоятельная проверка (не тестами исполнителя)

**S1. Одного писателя видно на диске.**
Заставить две роли переписать один и тот же scene-блок одновременно.
→ Правки сериализованы; итоговое содержимое файла соответствует одной из версий целиком, а запись в `scene_index` — этому же содержимому. Смеси двух версий нет.
Замер: снять содержимое файла и соответствующую запись индекса до и после — расхождение между ними и есть та поломка, ради которой пакет существует.

**S1a. Индекс не откатывается назад.**
Запустить два прогона на **разные файлы одного слага** так, чтобы их пересборки индекса наложились.
→ В итоговом `<slug>.json` присутствуют обе правки.
Это отдельный от S1 сценарий и он важнее: замок на путь файла его **не** ловит — файлы разные, гонка идёт за общий индекс, который пишется позже и без атомарной подмены (`scene-index.ts:151`).
Фальсификация: снять claim с индекса, оставив его на файлах, — проверка обязана упасть. Если проходит и так, наложения пересборок не воспроизвелось и наблюдение ничего не доказало.

**S1b. Персона не смешивается.**
Заставить два прогона переписать `persona.md` одновременно.
→ Итог равен ровно одной из двух версий.
Сегодня inline-L3 при включённой консолидации отключён (`utils/pipeline-factory/l3-runner.ts:26`), но обе роли внутри консолидации несут `rewritePersona` и остаются конкурентами — до правки эта проверка обязана падать.

**S2. Scratch уехал туда, куда сказано.**
Поставить `scratchRoot` instance одной роли во временный каталог, запустить прогон; отдельно повторить через legacy `runtime.scratch_root`, чтобы проверить адаптер.
→ Артефакты появились в нём; в прежнем месте (`join(dirname(dataDir), "tdai-memory-keeper")`) для этой роли ничего нового не создано.
Фальсификация: сегодня путь захардкожен (`server.ts:171-174`), поэтому до правки наблюдение даст обратное.

**S3. Прогон можно разобрать постфактум.**
Запустить роль с `keep_scratch: true`, дождаться завершения, зайти в каталог попытки.
→ На месте `run.json`, `input/workset.json`, `out/result.json`, `out/critic.json`; по ним восстанавливается, что роль получила на вход и что предложила.
Сегодня каталог удаляется (`day-runner.ts:119`, `night-runner.ts:112`) — до правки разобрать нечего.

**S4. Промпты не разъехались с кодом.**
После перевода входа на новое место прогнать роль, чьи скиллы ссылались на `diff.json`.
→ Роль отработала, вход прочитан; `scripts/sync-memory-skills.sh` не показывает расхождений зеркала.
Фальсификация: временно вернуть старое имя входа — должен сработать fallback, а не падение.

**S5. Inline-гейт не сняли по дороге.**
При включённой консолидации проверить, что inline-L2 по-прежнему no-op.
→ Сцены пишет только владелец артефакта. Если после правок их начал писать и inline-путь, single-writer сломан именно этим пакетом.

**S6. Каталог сцен целиком никто не сносит.**
Снять снимок `scene_blocks/` (список файлов и их mtime), прогнать полный цикл при `consolidation.enabled`, снять снимок снова.
→ Изменились только те файлы, которые применил apply. Ни одного файла, удалённого и созданного заново; каталог не пересоздавался.
Это проверка на `profile-sync` (A1c): он делает `rm -rf` каталога и `rename` поверх (`profile-sync.ts:151-155`), и на снимке это видно как «все файлы разом получили новый inode», даже если содержимое совпало.
Фальсификация: временно выключить `consolidation.enabled` и повторить — путь обязан сработать и снимок обязан показать полную подмену. Если не показывает, наблюдение слепо и первая половина ничего не доказала.

## Нефункциональные

- Отказ по конфликту блока — быстрый и явный (не ожидание с таймаутом).
- Retention scratch по умолчанию не увеличивает диск более чем на объём одного прогона на роль.

## Риски

- **R1 (medium)**: claim по связке `scene:<slug>` крупнее, чем по файлу, поэтому два прогона по разным файлам одного проекта теперь сериализуются, а не идут параллельно. План: слаг — проектный, конкуренция внутри одного проекта редка; если станет узким местом, дробить ресурс можно только вместе с решением проблемы общего индекса, а не вместо него.
- **R1a (low)**: сужение пересборки индекса до затронутых слагов может оставить несинхронизированным слаг, изменённый мимо apply. План: полная пересборка остаётся доступной отдельной операцией обслуживания.
- **R2 (low)**: сохранение scratch увеличивает диск. План: retention по умолчанию короткий, `keep_scratch` — явный opt-in.

## Risk tier

**Tier-2**: меняется владение записью L2 и путь артефактов; данные памяти не мигрируют.

## Откат

- Гейт по ресурсу — за флагом; откат возвращает per-role ключ.
- `scratchRoot` при отсутствии instance-поля (и legacy `runtime.scratch_root`) резолвится в прежний путь, поэтому откат не требует миграции.
- `keep_scratch` аддитивен; удаление поля возвращает текущее поведение.

## Глоссарий

- **Scene block** — markdown-файл `scene_blocks/<projectSlug>/*.md` плюс запись в `.metadata/scene_index/<slug>.json`. Не таблица.
- **Single scene writer** — взаимное исключение по ключу блока/слага, не по имени роли.
- **Inline-гейт** — намеренный no-op inline-L2 при включённой консолидации.
