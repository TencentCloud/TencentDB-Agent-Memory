# TZ-09: протокол прогона и безопасность apply (Phase 1.5)

> Источник: производный пакет, [agent-architecture.md](../agent-architecture.md) §3.1 (claim/lease/fence), §4.2–4.4 (отказы, вердикт, partial apply), §8 шаги 3, 8, 9
> Факт-чек кода: 2026-08-10

## Контекст

Между «контракт управляет исполнением» (tz-01) и любым боевым запуском generic-пути лежит слой, которого сегодня нет вовсе: у прогона нет ни идентичности, ни состояния, ни защиты от параллельного применения.

Проверено:

- в `RunSummary` нет даже `runId` (`consolidation/types.ts:34`), в payload apply — тоже (`apply-executor/types.ts:47-58`);
- мутации идут последовательно (merge → rewriteRecord → delete → files, `apply-executor.ts:93`), ошибка приходит после части изменений, но признак частичности не выставляется — статус просто `failed` (`apply-executor.ts:104`);
- `assertOpsSubset` определён (`apply-executor/validate.ts:44`) и экспортирован (`apply-executor.ts:23,58`), но в `apply()` не вызывается (`:84-95`);
- критик не является гейтом: после `preApply` идёт apply (`runner.ts:47`), доказательства одобрения именно этого кандидата у родителя нет;
- single-flight есть только per role (`role-gate.ts:25`) — apply разных ролей идёт параллельно.

Пока этого слоя нет, включать generic-apply нельзя: он уже умеет merge/delete/rewrite, и откат feature-флага этих мутаций не вернёт.

## Цель

Сделать прогон адресуемым и применение безопасным до того, как generic-путь получит право писать в память.

## Ожидаемый результат

- У прогона есть идентичность, состояние и durable-репозиторий; ретрай, отмена и частичное применение имеют куда записаться.
- Ровно одна активная попытка на Run и ровно один обработчик в apply.
- Частичное применение — терминальное состояние с реконсилиацией, а не тихий `failed`.

## Scope

**Входит:**

- `RoleRun` / `LaunchAttempt` / `CriticAttempt`, состояния и переходы (§3.1 модели).
- Attempt-claim и apply-claim с lease `{owner, expiresAt, fence}`, takeover, правила отмены и ретрая.
- Стадия критика в ядре с fail-closed и схемой вердикта (§4.3).
- `assertOpsSubset` и caps на каждом apply.
- Журнал операций по `operationId` с postcondition'ами и реконсилиацией (§4.4).
- Store-wide сериализация apply.

**Не входит:**

- Резолв контракта — tz-01 (предшественник).
- Checkpoint finalization — следующий обязательный deliverable tz-03a. tz-09 предоставляет durable Run/apply state, но не владеет checkpoint-инвариантами.
- Форма запуска и корни путей — tz-06 / tz-07.

**Инварианты пакета** (все — из §5 модели):

| Инвариант | Проверка |
|---|---|
| `single-apply-per-store` | `[t]` два apply разных ролей параллельно → сериализованы, порядок мутаций в журнале не переплетён |
| `core-owns-apply` | `[t]` ребёнок пробует прямую запись в `dataDir` и вызов `/memory/apply` своим токеном → отказ на обоих путях |
| `caps-enforced` | `[t]` операция вне `ops_subset` и кандидат сверх cap отклонены до мутаций; `[a]` каждый путь в `apply()` проходит через `assertOpsSubset` |
| `critic-before-apply` + `critic-fail-closed` | `[t]` apply без вердикта, с битым вердиктом и с вердиктом на другой `candidateDigest` → отказ во всех трёх |
| `candidate-bound-to-input` | `[t]` подмена `inputDigest` в `out/result.json` → apply отклонён |
| `stale-fence-rejected` | `[t]` takeover по истёкшему lease, затем записи прежнего владельца (`out/result.json`, `out/critic.json`, receipt) → все отклонены |
| `idempotent-apply-by-run-id` | `[t]` тот же apply дважды → счётчики и содержимое стора идентичны |
| `partial-apply-requires-reconciliation` | `[t]` сбой на 2-й из 3 операций → Run в `needs-reconciliation`, журнал перечисляет `verified`/`prepared`; checkpoint проверяет tz-03a |
| `cancel-means-no-late-apply` | `[t]` cancel во время `running` + поздний apply прежним владельцем → отклонён по fence |
| `contract-snapshot-pinned` | `[t]` правка `role.json` между попытками одного Run → вторая идёт по пиннутому контракту |

## Зависимости

Предшественник — tz-01 (нужен резолвнутый контракт и binding). После полного tz-09 обязательно идёт tz-03a; только цепочка `tz-09 → tz-03a` открывает shadow/cutover. tz-09 публикует verified Run state, а tz-03a единолично владеет `checkpoint-after-complete-apply` и `checkpoint-cursor-monotonic`.

## Требования (функциональные)

- **P1**: `RoleRun` неизменяем внутри себя: роль, версия, `contractHash`, binding и `inputDigest` пиннятся при создании. Ретрай — новый `LaunchAttempt` того же Run.
- **P2**: репозиторий Run/Attempt — серверный и durable; `run.json` в scratch остаётся копией для человека, а не источником истины (scratch удаляется — `day-runner.ts:119`).
- **P3**: attempt-claim линеаризует **старт** попытки, apply-claim — вход в мутацию. Одного apply-claim недостаточно: без первого две попытки параллельно доходят до `reviewed`.
- **P4**: fence проверяется на **любой** записи в состояние Run, а не только перед мутацией.
- **P5**: Run, застрявший в `applying`, выходит только через реконсилиацию; автоматический повторный вход по истёкшему lease запрещён.
- **P6**: политика и кандидат для apply берутся **из серверного репозитория по `runId`**, а не из HTTP-payload.
- **P7**: `operationId = hash(runId, candidateDigest, opIndex)`; у каждого типа операции — postcondition, проверяемый чтением. Операция без postcondition не имеет права быть в `ops_subset`.
- **P8**: журнал живёт в локальной control-plane SQLite независимо от бэкенда памяти; для не-SQLite операций работает saga без компенсаций (рекавери идемпотентным повтором).
- **P9 (классы отказа и ретраи, §4.2)**: реакция определяется классом, а не общим «повторить»:

  | Класс отказа | Реакция |
  |---|---|
  | transient launcher/provider | новый `LaunchAttempt` того же Run |
  | невалидный вывод роли / reject критика | новая попытка либо terminal reject по policy роли |
  | невалидный вывод **критика** | новый `CriticAttempt` над тем же кандидатом, не перегенерация |
  | конфликт манифеста/стора (устарел workset) | **новый Assignment и новый Run** с новым workset — не ретрай старого |
  | partial apply | не ретрай, а реконсилиация (P7) |
  | timeout / cancel | kill процесса и потомков, поздний apply запрещён |

  Бюджет ретраев принадлежит роли (поле контракта, резолвится в tz-01) и конечен. Терминальны для Run: `applied`, `cancelled`, `needs-reconciliation` и исчерпание бюджета (последняя попытка фиксируется как `failed-terminal`). `failed` и `rejected` терминальны для попытки, но не для Run. Fail-open допустим для advisory-аудита, но **не** для критика перед мутацией — там fail-closed.
- **P10 (наблюдаемость, §4.1)**: Run-репозиторий хранит именно этот состав, иначе разбор инцидента невозможен: `runId` / `assignmentId` / `attemptId` / ссылка на `HostSession`; `roleId` + `roleVersion` + `contractHash`; `binding` (host, provider, model, thinking); дайджесты входа, кандидата и вердикта; таймстемпы и переходы состояний; исход попытки (`code` / `signal` / `timeout` / `cancel`); receipts критика и apply; пути к сессии, scratch и логам; класс ошибки.
- **P11 (bootstrap критика)**: `critic_role` резолвится при создании Run в полноценные versioned package + instance binding + output schema. Prompt без manifest/contract не считается ролью. Отсутствующий или host-incompatible критик переводит основную роль в `disabled(reason)` до запуска. In-session critic legacy pi-extension допускается только в старом адаптере и не удовлетворяет generic fail-closed gate.

## Критерии приёмки

Полный список — таблица инвариантов выше; каждая строка является критерием. Дополнительно:

1. `[t]` Payload apply без `runId` отклоняется; с `runId`, которого нет в репозитории, — тоже.
2. `[t]` Два обработчика, одновременно увидевшие `reviewed`, дают ровно один вход в `applying`.
3. `[t]` Рекавери после смоделированного краша на каждом из четырёх состояний журнала (нет записи / `prepared` / `applied` / `verified`) приводит стор в согласованное состояние.
4. `[a]` В `apply()` нет пути, минующего `assertOpsSubset` и caps.
5. `[t]` Включение гейтов в shadow-режиме логирует расхождения и ничего не блокирует; переключение в fail-closed блокирует те же случаи.
6. `[t]` Для каждого живого `critic_role` существуют versioned package, instance `ExecutionBinding` и output schema. Missing manifest, invalid schema и host-incompatible binding переводят основную роль в `disabled(reason)` **до** создания LaunchAttempt основной роли.
7. `[t]` Synthetic critic возвращает negative verdict на заведомо плохой кандидат; apply не вызывается, receipt связан с тем же `candidateDigest`.

## План

1. Репозиторий Run/Attempt + durable-хранилище payload'ов (§8 шаг 3).
2. Bootstrap критиков: package + instance binding + schema fixtures для каждого живого `critic_role`; pre-launch disable на missing/invalid/host-incompatible.
2a. Стадия `CriticAttempt`, synthetic negative-verdict smoke и схема вердикта.
3. `assertOpsSubset` и caps — сначала shadow, затем fail-closed.
4. Claim/lease/fence на старт попытки и на apply.
5. Журнал `operationId`, postcondition'ы, реконсилиация.
6. Store-wide сериализация apply (§8 шаг 9).

## Самостоятельная проверка (не тестами исполнителя)

Пакет стоит на пути мутаций памяти, поэтому проверять надо не «тест зелёный», а поведение системы под сбоем. Все точки выполняются на тестовом сторе с копией боевых данных.

**S1. Гейт действительно закрыт.**
Подсунуть кандидата с операцией вне `ops_subset` роли (например `deleteL1` для роли, у которой его нет).
→ Apply отклонён, в сторе **ничего** не изменилось, в Run-репозитории видна причина отказа.
Фальсификация: посчитать записи до и после. Сегодня `assertOpsSubset` не вызывается (`apply-executor.ts:84-95`), значит до правки операция пройдёт — это контрольный замер.

**S2. Критик — гейт, а не формальность.**
Запустить apply, физически удалив `out/critic.json`. Повторить с вердиктом, у которого `candidateDigest` от другого прогона.
→ Оба раза apply не состоялся. Ни одной мутации.
Фальсификация: подложить валидный вердикт — apply обязан пройти. Если проходит в обоих случаях, гейта нет.

**S3. Убитый прогон не дописывает.**
Запустить роль, дождаться стадии `running`, **убить процесс** (`kill -9`), дождаться takeover по истёкшему lease, затем позволить убитому владельцу (или его эмуляции) записать результат.
→ Запись отклонена по fence; состояние Run определяется новой попыткой.
Это ровно тот сценарий, ради которого вводится fence: без него в Run попадёт кандидат заброшенной попытки.
Фальсификация: повторить то же самое **без** takeover — то есть дать первой попытке нормально дописать результат. Она обязана пройти. Если отклоняется и она, дело не в fence, а в том, что запись сломана вообще.

**S4. Частичное применение не притворяется успехом.**
Смоделировать сбой на второй из трёх операций (например сделать scene-файл недоступным для записи).
→ Run в `needs-reconciliation`, **checkpoint не сдвинут**, журнал показывает, какие операции `verified`, а какие нет; следующий запуск роли заблокирован до реконсилиации.
Фальсификация: сегодня статус станет `failed` (`apply-executor.ts:104`), а признака частичности не будет — сравнить.

**S5. Рекавери после краша.**
Убить gateway в момент apply (по разу на каждое состояние журнала: до записи, на `prepared`, на `applied`).
→ После рестарта стор согласован, повторная финализация того же `runId` — no-op, дублей нет.
Замер: количество записей каждого типа до краша и после рекавери совпадает с ожидаемым, а не «примерно».

**S6. Два apply не переплетаются.**
Запустить две роли так, чтобы их apply пересеклись по времени.
→ В журнале операции двух прогонов идут блоками, а не вперемешку; итог стора одинаков при повторе эксперимента.
Фальсификация: временно отключить сериализацию и повторить — операции обязаны переплестись, а итог стора начать плавать между прогонами. Если и без сериализации всё стабильно, эксперимент не создаёт реальной конкуренции (роли не пересеклись по времени) и ничего не проверяет.

## Нефункциональные

- Claim и запись в журнал не добавляют заметной задержки к прогону: это локальные транзакции.
- Реконсилиация — явная операция (ручная или по расписанию), не тихий фон; Run в `needs-reconciliation` блокирует следующий запуск роли.

## Риски

- **R1 (high)**: fail-closed гейты могут остановить боевой keeper на кандидате, который раньше проходил. План: shadow-режим с логом расхождений, переключение после суток без расхождений.
- **R2 (high)**: неверный postcondition даёт ложный `needs-reconciliation` и ручную работу на каждом прогоне. План: postcondition на каждый тип операции покрывается тестом рекавери до включения.
- **R3 (medium)**: сериализация apply снижает пропускную способность. План: сериализация по стору, а не глобальная; конфликтующие ресурсы разводятся по проектам.

## Risk tier

**Tier-3**: пакет стоит на пути мутаций памяти. Каждый гейт включается сначала в shadow. Первая невозвратная точка всей миграции — первый боевой generic-apply, и он наступает **после** этого пакета.

## Откат

- Каждый гейт — за флагом, откат в shadow не теряет данных.
- Репозиторий Run аддитивен: без него старый путь работает как сейчас.
- Журнал и реконсилиация не мутируют память сами по себе.

## Глоссарий

- **Lease** — владение попыткой: `{owner, expiresAt, fence}`; истёкший перезахватывается с новым fence.
- **Fence** — монотонный счётчик Run; запись с меньшим значением отвергается.
- **operationId** — стабильный между рестартами идентификатор операции внутри кандидата.
- **Postcondition** — проверяемое чтением утверждение о состоянии стора после операции.
