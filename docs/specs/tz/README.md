# Пакеты ТЗ — трассируемость и порядок

Десять пакетов, сведённых к одной модели: [agent-architecture.md](../agent-architecture.md). Исходные требования — [requirements-memory-agents-draft.md](../requirements-memory-agents-draft.md) §10.

Пакеты правились по факту кода: часть исходных требований опиралась на несуществующие файлы, таблицы и предпосылки. Каждое такое расхождение отмечено в таблице ниже и разобрано в самом пакете.

## Граф зависимостей

```text
tz-01 (корень: контракт управляет исполнением)
  ├─→ tz-09  протокол прогона и apply ──┐
  │      └─→ tz-03a checkpoint protocol │
  ├─→ tz-02  scene-writer + bundle      │  всё это — ДО cutover
  ├─→ tz-06  RoleLauncher ····┐         │
  └─→ tz-07  host-neutral ····┘ (1)     │
                                        ▼
                              ═══ cutover (§8 шаг 11) ═══
  ├─→ tz-03b  счётчики через точку коммита
  │     └─→ tz-05  scopes + provenance
  │           └─→ tz-08  потребитель памяти
  └─→ tz-04  recall (после tz-02 в части сцен)

tz-10 session isolation ── независимый safety-track до сквозной E2
tz-10a item diagnostics + project corpus ─→ tz-04 baseline/scoring ─→ tz-10b assembler cutover
tz-10 pre-tz-05 projection ─→ tz-05 native scope/provenance enrichment
```

Уточнения к связям:

- **tz-03 больше не предшественник tz-04.** Прежняя зависимость шла через `memory_counters` — таблицу, которой не существует.
- **(1) tz-06 и tz-07 независимы по коду, но упорядочены по выкатке**: снятие `--no-session` (tz-06) не выкатывается раньше retention сессий (tz-07 H5), иначе сессии растут неограниченно. Владелец retention — tz-07, единственный.
- **tz-02 → tz-06 односторонняя**: полная форма `inspectable-run` требует лога сессии, который появляется только после снятия `--no-session`. tz-02 проверяет файловую часть, tz-06 — сессионную.
- **tz-09 обязателен до cutover целиком.** Первый боевой generic-apply — первая невозвратная точка миграции; всё, что делает apply безопасным, идёт до неё.
- **tz-03 имеет два явно разделённых deliverable.** `tz-03a` (idempotent/monotonic checkpoint finalization) входит в pre-cutover gate вместе с tz-09. `tz-03b` (commit observer и derived counters) идёт после cutover. Нельзя закрыть пакет наполовину одним общим статусом: в трекере это две задачи с разной зависимостью.

Три инварианта проверяются частично более чем в одном пакете. Это не двойное владение: владелец один, остальные проверяют свой срез и ссылаются на полную форму.

| Инвариант | Полный владелец | Частичная проверка |
|---|---|---|
| `contract-drives-execution` | tz-01 | tz-02 — модель роли на пути L2 |
| `backend-parity` | tz-03 | tz-05 — scope и provenance на обоих бэкендах |
| `inspectable-run` | tz-06 (сессионная часть) | tz-02 — файловые артефакты; tz-07 — расположение под новым корнем и retention |

`checkpoint-after-complete-apply` и `checkpoint-cursor-monotonic` — соседние, но разные: первый про «не двигать при незавершённом apply», второй про «не откатывать при параллельных прогонах». **Оба принадлежат deliverable tz-03a**, а tz-09 предоставляет ему транзакционный control-plane и использует результат. Поэтому зависимость однозначна: tz-09 durable Run/apply repository → tz-03a checkpoint finalization → shadow/cutover. После cutover выполняется tz-03b с commit observer и derived counters. Верхний граф и таблица показывают именно этот порядок; отдельного правила «при расхождении верить другому разделу» больше нет.

## Приёмка

У каждого пакета — таблица инвариантов с исполняемой проверкой; полные формулировки в §5 модели. Маркеры: `[t]` рантайм-тест, `[a]` AST/import-чек по исходникам, `[f]` проверка артефактов на диске.

Grep допустим только в `[a]`-чеках и только с явным списком исключений. Проверка вида «в тексте пакета встречается слово INVARIANT» приёмкой не считается: она зеленеет на закомментированном коде.

**tz-04 — единственный пакет без инварианта.** Качество recall не выражается булевым свойством; приёмка идёт по `precision@5/@10` против baseline (§9 модели). Искать для него строку в §5 не нужно.

## Самостоятельная проверка: пакет не закрыт, пока не отработал вживую

В каждом пакете есть раздел «Самостоятельная проверка» с точками `S1…S6`. Это **не дубль критериев приёмки**, а защита от того, что критерии подгонят под реализацию: тесты пишет тот же, кто пишет код, и «зелено» означает лишь согласованность кода с собственным тестом.

Правила:

1. **Точки S выполняются на живом пайплайне**, а не на моках: реальный gateway, реальные роли, копия боевых данных.
2. **Замер «до» снимается заранее.** Половина точек устроена так, что до правки наблюдение даёт обратный результат (курсор откатывается, счётчик задваивается, роль игнорирует свою модель). Без замера «до» нечем доказать, что изменилось именно поведение, а не формулировка.
3. **Каждая точка фальсифицируема**: указано, что сломать, чтобы проверка упала. Проверка, которая не умеет падать, ничего не проверяет.
4. **Пакет закрыт, когда прошли и критерии, и точки S.** Зелёные тесты при непройденной точке S означают, что тест описывает не то поведение.

### Сквозная приёмка: пайплайн работает

Отдельно от пакетов — проверка того, ради чего всё делается. Выполняется на живой установке, целиком. E8 и E9 — **до** cutover (враждебный ребёнок и откат обязаны быть проверены раньше, чем система получит право писать), остальные — после.

**E1. Роль, которой вчера не было.**
Положить новый пакет роли (манифест + промпт + свой `ops_subset`), не трогая код.
→ Роль появилась в реестре, запустилась по своему расписанию, выдала кандидата, прошла критика, применилась. Ни одной правки в `src/`.
Это интегральная проверка всей затеи: если новая роль требует кода, generic-архитектуры нет.

**E2. Полный цикл памяти.**
Провести сессию → дождаться keeper'а → убедиться, что появились L1-записи и обновились сцены → сделать recall в новой сессии.
→ Найдено то, что обсуждалось; в выдаче нет чужого проекта; счётчики совпадают с фактом.
Параллельно провести вторую сессию с конфликтующим маркером → ни один O1/O1.5/O2/O3/O4 state/artifact/result не пересёк session boundary; diagnostics показывают identity/scope каждого включённого элемента.

**E3. Ночной проход не теряет и не задваивает.**
Прогнать night на копии боевого стора, сравнить снимки до и после.
→ Дубликаты сократились, ничего нужного не удалено, курсор сдвинулся вперёд ровно на обработанное, счётчики сошлись с `COUNT(*)`.

**E4. Сбой посреди применения.**
Убить gateway в момент apply.
→ После рестарта: стор согласован, Run в `needs-reconciliation` либо `applied`, checkpoint не ушёл вперёд применённого, повторный запуск не задваивает.

**E5. Смена хоста.**
Перевести одну роль на второй launcher.
→ Отработала, кандидат разобран так же; сессия читается; в ядре не появилось pi-флагов.

**E6. Память из другого клиента.**
Из сессии под Claude Code или Codex выполнить поиск и записать заметку.
→ Ответ тот же, что под pi; заметка появилась в памяти один раз.

**E7. Прогон разбирается постфактум.**
Взять любой недавний прогон и восстановить по артефактам: что было на входе, что предложила роль, что сказал критик, что применилось.
→ Восстанавливается полностью, без чтения кода и без догадок.

**E8. Враждебный ребёнок.**
Из процесса роли попробовать записать в память в обход ядра: прямой записью в `dataDir` и вызовом `POST /memory/apply` с токеном, который процесс сумел прочитать сам.
→ Оба пути отклонены.
Это проверка `core-owns-apply` как механики, а не соглашения. Сегодня утверждение «писать может только родитель» — happy-path convention: ребёнку передаётся настоящий `HOME` (`child-spawn.ts:71`), у хоста есть встроенные файловые тулы, а `GET /memory/info` без авторизации отдаёт `dataDir` и `tokenPath` (`info.ts:16-25`). Контрольный замер «до» здесь особенно важен: он покажет, что оба пути сейчас **проходят**.

**E9. Откат живьём.**
Выключить feature-флаг generic-пути на работающей установке с боевыми данными.
→ Система вернулась на прежний путь, память цела, прогоны идут.
Откат, ни разу не проверенный на живых данных, — не план отката, а намерение. Проверять до cutover, а не после того, как он понадобится.

**E10. Роль не может зациклиться.**
Заставить роль стабильно выдавать невалидный результат (или критика — стабильно отклонять).
→ Ретраи закончились в пределах бюджета, Run в `failed-terminal`, память не тронута, следующий запуск по расписанию произошёл штатно.
Без этой проверки бюджет ретраев остаётся числом в контракте, которое никто не проверял на конечность.

Пока E1–E10 не прошли на живой установке, миграция считается незавершённой, сколько бы пакетов ни было отмечено как готовые.
