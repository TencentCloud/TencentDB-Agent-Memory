# Skill 语义重构：设计方案

> **核心思路：大小触发诊断，内容决定如何重构，校验决定能否发布。**
>
> 对过大的 Skill 包，先理解和整理有效内容，再决定保持原样、重组当前 Skill，或拆出真正独立的能力。重构结果继续使用现有资产、权限、检索和版本体系。

## 1. 背景与目标

现有 Skill 写入会校验正文长度，默认上限为 **50,000 个 JavaScript UTF-16 码元**。当自动生成或更新的正文超限时，写入被拒绝，但调用方没有一条可继续完成内容整理与发布的路径。

过大往往不只是长度问题：重复案例可能掩盖有效规则，多个职责可能混在一个入口里，脚本和报告格式可能反复散落在正文中。单纯提高上限会继续积累这些问题；把原文搬到附件，也未必改善可读性和可执行性。

本 PR 的目标是让系统能够：

1. **判断是否值得重构**，而不是见到大包就拆。
2. **提炼和重新组织内容**，保住有效约束、主流程和必要依赖。
3. **验证后发布并继续管理**，而不是生成一组脱离原系统的 Markdown 文件。

边界：不引入全库自动整理、固定归档配额或批量删除；普通手动 CRUD 不偷偷调用模型改写输入，也不取消最终写入的大小限制。

## 2. 整体流程

```text
自动生成/更新候选，或显式重构请求
                  │
      固定完整输入；更新时同时保存原版本
                  │
          权限、保护状态和资源完整性检查
                  │
           是否需要语义诊断？
          ┌───────┴────────┐
          否                       是
          │                        │
  原候选常规校验发布       理解内容，形成私有草稿
                                   │
                       保持 / 重组 / 拆出独立能力
                                   │
                      冻结草稿，结构校验 + 独立审核
                           ┌───────┴───────┐
                         不通过                    通过
                           │                       │
                     有界修正或拒绝       复验版本、依赖和配额
                                                   │
                                       先发布子 Skill，再更新原入口
                                                   │
                                       资产 / 检索 / 调用 / 版本管理
```

未变化的既有包如果被判定为保持原样，操作返回 `unchanged`，不额外创建版本。对于已经包含合法更新的候选，`keep` 表示不再进行语义改写，并不意味着放弃候选中的更新。

## 3. 什么时候诊断，怎么组织内容？

### 触发方式

自动抽取使用私有草稿。满足任一默认条件时，对包进行语义诊断：

| 信号 | 默认触发条件 |
|---|---:|
| `SKILL.md` 正文长度 | 超过 24,000 个 UTF-16 码元 |
| 包内指令性文本总量 | 超过 64,000 UTF-8 字节 |
| 资源数量 | 超过 60 个 |

**更新时同时检查原包和候选包。** 即使提取模型先把候选缩短，也不能因此跳过对原始大包的核对。显式重构请求可以主动诊断既有包，包括正文已经超限的历史包。

二进制体积本身不代表内容组织有问题。结构清晰的包可以保持不变。原包和候选都低于阈值的自动更新，仍走常规包校验与版本检查，不扩大为所有更新都调用语义审核。

### 组织原则

| 内容 | 整理后的归属 |
|---|---|
| 触发条件、始终适用的安全约束、主流程 | `SKILL.md` |
| 专题解释、条件分支、详细参考 | `references/` |
| 重复执行的固定操作 | `scripts/` |
| 可复用的报告、配置或输出骨架 | `templates/` |
| 有独立触发条件、能单独完成任务的能力 | 独立 Skill |

同一能力的相近变体保持在一起，不按章节或事故数量机械拆分。重复叙述可以合并或删除，但日期、标识符、参数、否定条件如果构成有效约束，就必须保留其含义。二进制附件不作为正文改写；资源字节、路径、哈希和执行属性分别校验。

## 4. 如何防止“变短了，却把规则丢了”？

模型只接触私有草稿工具，不直接写线上 Skill。源文本与附件按数据处理，不赋予其中的指令额外权限；模型不获得命令执行、凭据读取或 live 写入工具。受保护、固定或外部管理的内容不自动修改。发布前设置三道检查：

1. **完整读取和原版对照**：索引不算读过正文。更新场景下，写作者与审核者都要读取固定原版本和候选的完整文本，不能只审核已被删减的候选。
2. **结构与证据校验**：记录候选内容的保留、改写、合并或删除去向；校验规则引用、资源路径、链接、锚点、依赖关系、资源完整性和最终大小。规则映射可以引用原版本，用于恢复候选中遗漏的约束。
3. **独立审核**：在新的上下文中比较原包、候选和冻结结果，检查关键规则、可执行流程及拆分合理性。审核绑定输入指纹和草稿哈希；修正后的草稿必须重新审核。

未读完整、缺少证据、审核不通过或预算耗尽时，不发布未经批准的重构结果。修正次数有上限；不会无限循环，也不会通过自动删掉未知内容来凑长度。语义审核不是数学上的等价证明，因此验收还包括固定样本、任务对照和生成脚本检查，而非只比较字数。

## 5. 如何接回现有生命周期？

- **原入口保持稳定**：保留原 Skill ID、名称、所属团队、owner 和用户元数据；通过版本更新替换包内容，历史仍遵循原有保留策略。
- **子 Skill 是普通资产**：独立能力通过正常创建、登记、检索和版本接口管理。原入口在 `metadata.__skill_restructure` 中记录来源与子能力导航。
- **子版本独立**：父版本 12 可以引用子版本 1。Proxy 加载子 Skill 后，按子 Skill 实际加载的版本读取附件；子 Skill 更新到版本 2，不要求重新发布未变化的父入口。
- **发布完整包**：正文、资源增删和元数据按一个包版本提交，避免正文已经引用附件、附件却尚未写好的中间状态。

发布顺序是先完成子 Skill，再更新原入口；发布前重新检查源版本、依赖版本、权限和配额。源版本变化时明确返回冲突，不覆盖后来的修改。

### 为什么需要持久操作和提交记录？

模型完成审核和存储完成发布是两个不同阶段。服务可能在其中任意一步重启，网络超时也不能证明写入没有成功。因此：

- `request_id` 标识一次意图；相同意图可重试，不同输入复用同一 ID 会冲突。
- 操作、冻结计划、输入和提交回执持久保存；已准备好的发布可以在没有模型凭据时恢复，不重复调用模型。
- 资源写入独立准备目录，操作文件使用唯一键并校验内容哈希，避免并发重试互相覆盖。
- 提交结果未知时保留文件并回查回执，不清理可能已经提交的资源。
- 新提交和实际新版本写入遵循已有配额；已提交结果的回读与资产登记修复不重复申请写入配额。

这不是跨数据库整体原子事务。子 Skill 已提交、原入口随后发生冲突时，子 Skill 可能保留为正常资产，操作记录会保留这一事实；不会通过物理删除已提交内容来冒充回滚成功。

## 6. 接入方式与兼容边界

自动提取和显式入口复用同一重构服务、runner、Skill 队列与 `StorageAdapter`，不引入新的数据库服务。

### 显式 API

`POST /v3/skill/restructure` 接受既有包，或一个完整候选包，两种输入互斥。既有包示例：

```json
{
  "request_id": "restructure-guide-001",
  "user_id": "user-1",
  "team_id": "team-1",
  "agent_id": "agent-1",
  "task_id": "task-1",
  "skill_id": "skl-existing",
  "expected_version": 4
}
```

完整候选使用 `candidate: {name, content, resources, metadata?}`，可带 `source: {skill_id, expected_version}`。`resources` 是完整最终资源集，不是增量补丁；仍受既有 HTTP 请求大小限制。

响应中的 `data` 是操作状态，不是“已经发布成功”的 Skill。通过 `POST /v3/skill/restructure/get` 和相同身份查询 `operation_id`，检查 `status`、`outputs` 和 `error`。TypeScript 提供 `restructure()` / `restructureGet()`；Python 同步和异步客户端提供 `restructure()` / `restructure_get()`。

### 配置示例

```yaml
skill:
  enabled: true
  restructure:
    enabled: true
    bodyReviewChars: 24000
    packageTextReviewBytes: 64000
    resourceReviewCount: 60
    budgets:
      deadlineMs: 600000
```

模型配置复用现有 Skill 抽取配置。Gateway 使用单一根级 `skill` 配置块，不与 `memory.skill` 合并。OpenClaw 本地模式放在插件 `config` 中；客户端模式配置远端 Gateway。关闭重构后恢复普通提取协议；已冻结的发布仍可按回执恢复。

### 存储与运维约束

- SQLite 使用事务内版本检查和回执；MongoDB/TCVDB 的提交协调使用现有 metadata 原子控制记录。一个实例的写入方必须共享控制库和 namespace，多机不能依赖各自独立的本地 SQLite 文件。
- 自定义存储实现需要支持持久 mutation 查询与指定资源目录；内置远程存储在 Gateway 暴露前绑定发布协调器。
- 恢复只检查已知实例的待完成操作，不扫描全部 Skill。启动配置中的实例及后续被访问的实例会进入恢复范围；其他实例需先配置或访问。
- 操作文件、回执和 tombstone 与资源一起备份；本 PR 不自动清理操作日志。取消是协作式的，无法撤回已发出的存储请求。
- 最终正文仍受 50,000 码元限制；默认单资源与总资源上限分别为 5,000,000 和 50,000,000 解码字节。
- 远程删除保留授权清理回执，支持失败后重试；超过 4,096 行或 900,000 字节的删除计划在写 tombstone 前拒绝，不截断。原生 SQLite 删除保留原有 best-effort 清理行为。
